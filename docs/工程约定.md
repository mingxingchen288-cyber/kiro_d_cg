- 连接信息和密钥只放在根目录的 `.env` 中（已被 git 忽略），不写进代码、日志和文档。前端也读取根目录的环境文件，只有 `VITE_` 开头的变量进入浏览器（assembly 的 AS-09）。
- 旧项目目录 `D:\chonggou\my-project`、`D:\chonggou\my-project-python`、`D:\chonggou\new\platform` 只作参照，不修改。

## 2. 工作规矩

- 安装新的工具链或系统组件之前，先征得用户同意。
- 不修改 git 配置；用户没有提供提交用的名字和邮箱时，不提交。
- 测试不跳过、不删除、不放宽断言。没有运行的测试写明原因，不算通过；有测试失败时，任务不标为完成。
- 出现以下情况时停下来问用户，不自行换方案：rules-core 可行性验证不通过；SQL 条数达不到 write-pipeline 的目标；前后端计算结果不一致。
- 实施中不自行用存储过程或原生 SQL 绕过写入管道；逃生舱只在用户点名时启用。
- 依赖待确认事项的部分，先取得用户的结论再实现。用户没有反对，不等于已经确认。

## 3. 文档规矩

- 文档只有一套，都在 `docs/` 下，目录见 [README](README.md)。
- 每条需求、规则、术语、接口和状态只在一个位置定义，其他地方用编号和链接引用。
- 用户修改需求时，直接修改对应的定义并同步受影响的引用，不另写变更记录。
- 待确认的内容列在所在文档末尾的"待确认"一节。

## 4. 任务状态与证据

- 状态取：未开始、进行中、待联调、完成。任务的"接入责任"写明它在哪个联调任务中接入：有联调任务的，通过自己的验收后为"待联调"，联调通过后为"完成"；没有的，通过验收即为"完成"。
- 证据分三种，分开记录：
  - 模拟验证：使用 contracts 的替代实现；
  - 真实验证：本模块自己的 Oracle 或 Redis 实现，在 d_cg 或 Redis 上运行；
  - 真实联调：assembly 把多个模块的真实实现接在一起运行。
- 证据写明运行的命令，以及通过和失败的数量；详细输出放在 `.reports/` 下。
- 接口已定义、模拟测试通过、文档已写好，都不等于真实业务流程已经完成。

## 5. 测试先行

以下逻辑先写失败的测试，再写实现；测试用例取自[业务例子](业务例子.md)和模块说明的规则：

| 逻辑 | 任务 |
|---|---|
| 计算、执行顺序、数值处理规则表 | T-RC-2、T-RC-3 |
| 十进制文本和数值一致判定 | T-CT-2 |
| 增量补丁：合并、变更计划、小数位处理、ERP 行 | T-WP-2 |
| 判重 | T-WP-1 |
| 单角色授权、按钮权限 | T-AZ-1 |
| 冻结判断、审批流转、单据只属于一个审批 | T-AP-1、T-AP-2 |
| 编辑缓冲、撤销重做 | T-FP-1 |

页面布局、配置表单、路由注册这类改动，以及已有测试充分覆盖的改动，不机械补测试，按任务的验收标准验证。

测试的范围（用户 2026-10-28："我让你测试的目的是把正向流程跑通即可，至于其它的奇怪的流程，可以以后再说"）：

- 只测正向流程：业务例子、用户点名的场景，以及数据是不是用户真实操作的数据。
- 不写防御性的用例和代码：异常、边界、并发竞争、配置写错之类的情况，用户没有点名的不做，上线后按实际出现的问题再补。不用"故意写错的实现"找测试漏洞。
- 前台和后台都只开放某项功能时，没开放的路径不另做校验和测试：两边都堵死，用户就绕不过去。
- 任务卡验收标准中用户没有点名的异常、边界条目，开工时标为"上线后再补"，不实施。
- 以审批为例，查询、冻结、展示都用通用模块；要做和要测的是：什么时候触发、什么时候冻结、什么时候解冻、什么时候把数据写入具体的表。

前端端到端测试（用户 2026-10-30："让前端端到端测试由代理写得快、跑得快"，做法见 `frontend/tests/e2e/playwright-base.ts`、`support.ts`）：

- 核对界面一律写成 `frontend/tests/e2e` 里的正式用例，用 `support.ts` 这一份工具（按页面编码打开、按 row-id 和 col-id 取格子、编辑、保存、读提示、经接口准备数据），不在 `.reports` 下写一次性脚本。能抽成函数的界面逻辑放进 vitest。
- 数据隔离：要写数据的用例用 `data` fixture 经平台接口建自己的测试数据（备注带 PF_TEST），用例结束自动删除，不改 2550 这类共用单据。改共用配置的用例标 `@shared-config`，在 e2e 项目之后单独跑，彼此用测试锁。
- 不用固定等待（waitForTimeout），等元素出现、等内容变化。数据库里的结果在用例里断言（经平台接口或只读查询），失败时才留 trace。
- 表格的列：两种运行方式都是测试模式（`vite --mode test`），主表、明细、Lookup 结果、配置页表格、审批的修改内容表格都关掉了列虚拟化（用户 2026-10-30 同意，只在测试模式下），一次渲染全部列，与窗口宽度无关（`columns.spec.ts` 核对成本核算主表 43 列、明细各 18 列）。所以 `cell()` 按 row-id、col-id 直接取格子，不横向滚动；点击、双击、悬停前由 Playwright 把格子滚到可见；只有悬停列头、点筛选按钮前用 `scrollToColumn` 滚一次。列显示与否看 `header()` 在不在。正式构建（`pnpm build`）仍开着列虚拟化，不用来跑这些用例。
- 运行：回归 `pnpm test:e2e`（先 `pnpm build:test` 测试模式构建，产物由后端托管）；开发 `pnpm test:e2e:dev`（Vite 开发服务器，`--mode test`）。服务由 webServer 起停，默认后端 8090、开发服务器 9540，环境变量只经 webServer 的 `env` 给子进程。平时用 `--grep`、`--only-changed` 只跑相关的，重跑用 `--last-failed`，`-x` 遇到第一个失败就停；只调 `@shared-config` 的用例加 `--project=shared-config --no-deps`；最后全量跑一次。

以下约束只有真实环境的结果才算证据，替代实现的测试不能代替：

## 7. 完成前的独立复核

- 任务标为"完成"之前，由没有参与实施的审查者复核。审查者自己读取：任务链接到的模块规则和业务例子、实际的代码差异、`.reports/` 下的原始验证输出，逐条判断是否满足，不只看实施者的摘要。
- 审查者按第 5 节的测试范围判断：正向流程和用户点名的场景跑通、数据正确，即可通过；不另行构造写错的实现或异常场景找漏洞。
- 复核记录放在 `.reports/review/<任务编号>.md`，写明逐条结论和发现的问题。正向流程有问题时任务保持"进行中"或"待联调"；"建议"不阻断完成，实施者不为它另做一轮修改和复核。
- 任务的"状态与证据"写上原始输出和复核记录的路径。
