## 2. db-core 提供

```python
class UnitOfWork(Protocol):
    connection: sqlalchemy.engine.Connection   # 本事务的连接，各模块的存储实现都用它
    def commit(self) -> None: ...
    def rollback(self) -> None: ...

class UnitOfWorkFactory(Protocol):
    def begin(self) -> ContextManager[UnitOfWork]: ...   # 退出时没有提交就回滚

class SchemaInspector(Protocol):
    def columns(self, table: str) -> dict[str, ColumnInfo] | None: ...   # 表或视图的列，不存在时为 None；键为列名
    def object_type(self, name: str) -> Literal["table", "view"] | None: ...   # 是表还是视图，都不是时为 None；审批的冻结表、修改表只能是表（C06 第 10 节）
    def primary_key(self, table: str) -> str | None: ...   # 表的单列主键列名；没有主键、主键多于一列或不是表时为 None（C06 7.5 的 keyColumn 省略时用）
    def column_comments(self, table: str) -> dict[str, str | None] | None: ...   # v21：表或视图每一列的注释，按列的顺序，没有注释的为 None；不存在时为 None（新建页面向导的列标题，config CF-20）
    def objects(self, keyword: str) -> list[DbObject]: ...   # v21：名称含关键字（不分大小写）的表和视图，最多 100 个，先表后视图、各按名称排列；关键字为空时不按名称筛选（向导搜表，C09 第 3 节）
    def view_sources(self, view: str) -> list[str] | None: ...   # v22：视图直接读取的表、视图和同义词，按名称排列；当前用户的只写名称，别的用户的写"用户.名称"，经数据库链接的另加"@链接名"；视图里调用的函数、包不算；不是视图时为 None（write-pipeline 判断读取视图是否只读实体自己的表，WP-03）

@dataclass(frozen=True)
class DbObject:
    name: str
    type: Literal["table", "view"]

@dataclass(frozen=True)
class ColumnInfo:
    name: str
    data_type: str                 # Oracle 的数据类型，例如 NUMBER、VARCHAR2、DATE
    nullable: bool
    length: int | None             # 字符列的长度
    precision: int | None          # 数值列的精度
    scale: int | None              # 数值列的小数位数，保存时据此处理小数位（write-pipeline WP-15）

class ConnectionFactory(Protocol):
    def legacy_readonly(self) -> ContextManager[sqlalchemy.engine.Connection]: ...   # 用 d_cg 账号开启只读事务（SET TRANSACTION READ ONLY），以 CMX.表名 读取旧库；只供 migration 和复制业务表使用
```

- 数值列读出为 `Decimal`，不经过浮点。
- Oracle 错误按 C03 映射：等锁超时和死锁（ORA-00060）为 DOCUMENT_BUSY，连接断开或数据库不可用为 DATABASE_UNAVAILABLE，其余为 INTERNAL_ERROR。

- 快照中缺少要取的配置项时（例如 Redis 没有命中），先按 config 的 CF-06 回查 Oracle 并补写，不直接报错。回查后仍取不到时：
  - `page_view`：页面不存在为 404 NOT_FOUND，该角色不能访问这个页面为 403 PERMISSION_DENIED，与 C09 的页面视图接口一致；
  - `entity`、`operation`、`approval_flow`、`rules_pack`：说明已发布配置的内部引用断了（保存时已校验引用），为 500 INTERNAL_ERROR。
- `read` 回查后确认该角色的角色配置已被删除时，抛 401 SESSION_ROLE_REVOKED，由用户重新选择有效的角色。已经取得的快照不受影响，持有它的请求和命令按它执行到结束（C04）。
- `import_items` 整批校验：有一项不通过时抛 422 VALIDATION_FAILED，明细列出每个不通过的项，什么都不写。
  - 同一批中有两项或更多项类型和编码相同时，按不通过处理，明细列出其中每一项：无法判断该保留哪一项，只取一项会让其余的悄悄不生效。这项检查在跳过已有配置项之前进行，重复的项与已有配置项相同时也拒绝。
  - 与已有配置项类型和编码相同的项不覆盖，列入 `skipped`，既不写入也不参与校验；其余各项与已有配置、本批的其他项一起校验，引用可以指向两者。
  - 错误明细的 `path`（C03 第 1 节）以这一项在本批中的位置 `items[<序号>]` 开头，序号从 0 起，内容中的位置接在后面，例如 `items[3].levels[0].nodes[1].approvers`；针对整项的错误（例如同批重复）只有 `items[<序号>]`。调用方据此找回这一项的来源（migration MG-11）。

## 5. orchestration 提供

```python
class CommandExecutor(Protocol):
    def execute(self, command: Command, ctx: ExecutionContext) -> CommandResult: ...
    # Command、CommandResult 见 C02。只涉及一张单据时失败抛 PlatformError，事务已回滚；
    # 按单据提交（C02 v10 第 1 节）时不抛 PlatformError，没成功的单据在结果的 failed 中
```

一个命令一个事务：`CommandRecorder.begin`（判重）→ 按 orchestration 的 `STAGE_ORDER` 依次执行各位置上 `applies` 为真的管道阶段（第 6 节）→ `CommandRecorder.complete`（命令结果、审计、逃生舱调用记录、命令记录）→ 提交 → `DeliveryDispatcher.dispatch_now`（投递）。从判重到提交或回滚包在 `CommandMonitor.watch` 中（命令审查，第 5a 节）。

v23 按单据提交（C02 v10 第 1 节）：页面保存带 2 张及以上单据、按钮选中 2 行及以上主表行时，先拆成每张单据一个子命令（子请求键由原请求键和单据决定，同一请求重发时相同），每个子命令照上面的步骤各自执行（各自判重、一个事务、各记一条命令审查和命令记录），按提交的先后；子命令抛 PlatformError 时把它的错误体记入结果的 `failed`，抛别的异常时记日志、按 500 INTERNAL_ERROR 记入，继续下一张；最后把各张单据的结果合成一个命令结果，请求键为原请求键。

## 5b. write-pipeline 提供的业务加锁入口

2026-10-30 由使用方 approval、operations 提出：它们要加的锁（审批记录、冻结对象、按钮找到的别的单据、审批最终通过要写的单据和行）必须和 write-pipeline 的加锁读取按同一顺序，而业务模块之间不能互相导入，所以单设端口。规则见 write-pipeline WP-03（用户 2026-10-30 同意"固定加锁层级"）。

```python
LockLayer = Literal["approval", "document", "base"]
LOCK_LAYERS = ("approval", "document", "base")      # 加锁的先后：审批记录（PF_APPROVAL）→ 单据层 → 基础数据层

@dataclass(frozen=True)
class LockTarget:
    layer: LockLayer               # 有 details 的主表实体为单据层（成本核算）；其余注册实体、没注册的表为基础数据层（物料清单）
    table: str                     # 物理表名（大写）：单据为主表实体的 table
    key_column: str                # 主键列（大写）
    key: str                       # 主键文本
    numeric: bool                  # 主键按数值比较（主键字段或列是数值类型）
    def order(self) -> tuple[int, str, Decimal | str]: ...   # 统一顺序：层级 → 表名 → 主键

class BusinessLocker(Protocol):
    def document(self, ctx: ExecutionContext, ref: DocumentRef) -> LockTarget: ...
    def row(self, table: str, key_column: str, key: str) -> LockTarget: ...   # 没注册的表中的一行（基础数据层）
    def approval(self, approval_id: str) -> LockTarget: ...                   # 审批记录，排在所有业务数据之前
    def layer(self, ctx: ExecutionContext, entity: str) -> LockLayer: ...    # 主表实体的层级
    def read(self, uow: UnitOfWork, ctx: ExecutionContext, refs: list[DocumentRef]) -> dict[DocumentRef, DocumentData]: ...
    # 加锁前的普通读取：主表和全部明细，不加锁；不存在的单据不在结果中
    def lock(self, uow: UnitOfWork, ctx: ExecutionContext, targets: list[LockTarget], expected: dict[DocumentRef, DocumentData] | None = None) -> None: ...
    # 按统一顺序一行一条 SELECT … FOR UPDATE WAIT n 锁住本事务还没持有的；expected 为加锁前普通读到的本命令单据，
    # 锁住后重读核对，不同时抛 LockScopeChanged；要锁的排在本事务已持有的锁之前时 500 INTERNAL_ERROR（实现错误）
    def held(self, uow: UnitOfWork) -> frozenset[LockTarget]: ...
```

- 一个事务中新加的锁必须排在已持有的全部锁之后（往后找）。要锁的对象排在已持有的锁之前或同层时（往前找、同层找），调用方先用普通查询找出范围（`read` 和本来就要执行的查询），再和自己的单据合在一起一次锁完；锁住后以锁住的这一批为准。
- `LockScopeChanged`：加锁前读到的本命令单据锁住后核对不一致，orchestration 回滚整个事务、整条命令重来一次（write-pipeline WP-13 的例外）。
- 加锁读取（write-pipeline 的管道阶段）、`TableWriter.lock_row` 与本端口共用同一份"本事务已持有的锁"，按同一顺序检查。替代实现为 `FakeBusinessLocker`。
- v23 主从单据连明细一起锁（用户 2026-10-31："如果是主从保存，那么主从都要锁"）：加锁读取，以及 `lock` 中 `expected` 的本命令单据，锁住主表行后再锁这张单据的全部明细行（每张明细表一条）；只冻结、不写的单据只锁主表行（write-pipeline WP-03）。明细行不是 `LockTarget`，不进"已持有的锁"。

## 6. 管道阶段

orchestration 按 `STAGE_ORDER`（[架构第 7 节](../架构与组装.md)）依次执行各位置上的阶段；阶段的 `name` 就是它所在的位置名，同一位置的几个实现由各自的 `applies` 决定这次执行哪个。阶段之间只通过 `CommandState` 传递数据。

`RelatedQuery.find` 的查找和来源行：

- 按关联键查找时，用 `source` 中 `sourceKey` 所指实体（主表或某个明细）的全部行的键值查目标。按关联键找到的对象 `missing` 总为 False。
- `finder.entity` 为明细实体时（例如按关联键找原辅料明细），找到的每一行明细为一个对象：`record_key` 为它所属主单的主键（按实体的 `details.parentKey`），`row_keys` 为这行明细的主键。加锁和冻结检查都按所属主单（WP-18）。
- 关联 SQL 的绑定变量只引用主表字段时，用 `source` 的主表行执行一次。引用某个明细的字段时，按 `source` 中这个明细的行的顺序逐行各执行一次，主表字段取主表行的值；这个明细没有行时不执行，结果为空。各次的结果按这个顺序合并，每次执行内按 SQL 返回的顺序；同一对象只保留第一次出现的那一个（连同它的 `display`），同一次执行查出的重复行也只算一个，只引用主表字段的 SQL 也一样：实体、`record_key`、`row_keys` 都相同的是同一对象，例如同一张成本单的两行原辅料明细 `row_keys` 不同，是两个对象；`missing` 的对象没有完整的主键，`record_key` 和 `display` 都相同的才算同一对象。用哪些行由调用方准备（见下面按钮操作一条），端口不再筛选。合并后的结果不带"由哪一行找到"：调用方需要按来源行给字段映射取值时（C06 第 6 节），关联键和关联 SQL 都按选出的行分别调用 `find`，每次只传入一行，几次的结果由调用方按同样的规则合并（按行的顺序，同一对象保留第一次出现的那一个）。
- 关联 SQL 的结果缺少 `recordKeyColumn` 列，或缺少 `rowKeyColumns` 中的列时，抛 500 INTERNAL_ERROR，整个查找失败，不返回部分结果：这是配置错误，无法判断要处理哪个对象。config 保存时已检查这些列（C06 第 10 节），运行时仍然缺少，说明保存之后表、视图或 SQL 引用的对象变了；不能把它当成"记录已不存在"跳过，否则配置错误会悄悄让同步失效。
- 关联 SQL 查出的某一行，`recordKeyColumn` 或 `rowKeyColumns` 中某列的值为空时，这一行表示的记录在查找时就已经不存在，例如成本单的明细还在，它所属的成本单已被删除。这一行照常返回：`missing` 为 True，`record_key` 为查到的单据主键（为空时为 None），`row_keys` 为空，`display` 照常取值；其余各行不受影响，也不报错。调用方不更新 `missing` 的对象。
- 按钮操作中的 `updateRecords`：operations 传入选中单据加锁后从数据库读到的当前数据，加上本命令前面各动作计算后的结果（`CommandState.current`、`candidate`），不用前端的值（C02 第 1 节）。按钮命令不带修改，关联键的 `rows` 只能为 `all`（C06 第 10 节）；绑定明细字段的关联 SQL 同样用选中单据的全部行（C06 6.1）。

## 14. 契约测试

- 每个端口一套测试，放在 `backend/tests/contracts/test_<端口名>.py`；`UnitOfWork` 与工厂、`ConfigSnapshot` 与读取方各在同一套测试中。contracts 的内存替代实现和各模块的真实实现都运行同一套测试。
- 每套测试写成 `<端口名>Contract` 类。被测实现和准备数据的方法由 `harness` fixture 提供，接口为同一文件中的 `<端口名>Harness` 协议。替代实现在同一文件中以 `TestFake<端口名>` 运行；真实实现在提供方自己的测试中继承同一个类，提供自己的 `harness`。
- 契约测试只检查本文和它引用的契约写明的接口行为。只由提供方模块规则决定的行为（例如 authz 的 AZ-01、config 的 CF-12）由提供方自己的测试验证。
- 替代实现通过契约测试，只说明它符合约定的接口行为；Oracle 的锁、并发和持久化等仍要在真实环境中验证（工程约定第 6 节）。
- 管道阶段的测试用 `CommandState` 样例，验证每个阶段只写上表中它负责的字段。
