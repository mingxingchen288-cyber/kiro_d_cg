# C08 后端端口

版本：v3。维护：contracts。状态：已确认。

端口和类型定义在 `backend/src/cost_platform/contracts/` 中：类型在 `types.py`，端口在 `ports.py`。contracts 为每个端口提供内存替代实现（`contracts/fakes/`），并提供一套契约测试（`backend/tests/contracts/`）。真实实现必须通过同一套测试。谁提供、谁使用见[架构第 8 节](../架构与组装.md)。

## 2. db-core 提供

```python
class UnitOfWork(Protocol):
    connection: sqlalchemy.engine.Connection   # 本事务的连接，各模块的存储实现都用它
    def commit(self) -> None: ...
    def rollback(self) -> None: ...

class UnitOfWorkFactory(Protocol):
    def begin(self) -> ContextManager[UnitOfWork]: ...   # 退出时没有提交就回滚

class SchemaInspector(Protocol):
    def columns(self, table: str) -> dict[str, ColumnInfo] | None: ...   # 表不存在时为 None；键为列名

@dataclass(frozen=True)
class ColumnInfo:
    name: str
    data_type: str                 # Oracle 的数据类型，例如 NUMBER、VARCHAR2、DATE
    nullable: bool
    length: int | None             # 字符列的长度
    precision: int | None          # 数值列的精度
    scale: int | None              # 数值列的小数位数，保存时据此处理小数位（write-pipeline WP-15）

class ConnectionFactory(Protocol):
    def legacy_readonly(self) -> ContextManager[sqlalchemy.engine.Connection]: ...   # 用 d_cg 账号开启只读事务（SET TRANSACTION READ ONLY），以 CMX.表名 读取旧库；只供 migration 和复制业务表使用
```

- 数值列读出为 `Decimal`，不经过浮点。
- Oracle 错误按 C03 映射：等锁超时为 DOCUMENT_BUSY，连接断开或数据库不可用为 DATABASE_UNAVAILABLE，其余为 INTERNAL_ERROR。

## 6. 管道阶段

write-pipeline 按[架构第 7 节](../架构与组装.md)的顺序调用已注册的阶段。阶段之间只通过 `CommandState` 传递数据。

```python
class PipelineStage(Protocol):
    name: str
    def applies(self, state: CommandState, ctx: ExecutionContext) -> bool: ...
    def run(self, uow: UnitOfWork, state: CommandState, ctx: ExecutionContext) -> None: ...   # 失败时抛 PlatformError

@dataclass
class CommandState:                              # 除 command 外各字段在命令开始时为空，outcome 为 None
    command: Command
    involved: list[DocumentRef]
    current: dict[DocumentRef, DocumentData]     # 加锁后读到的当前值
    actions: list[ActionStep]                    # 要执行的动作：C06 第 6 节的通用动作（afterApproval 或操作的 actions）
    candidate: dict[DocumentRef, DocumentData]   # 合并修改并计算后的数据
    effects: list[RuleEffect]                    # C07 effects[] 的项
    changes: ChangePlan                          # 只含有变化的列
    approvals: list[ApprovalState]               # 本命令提交或处理的审批；提交时每张提交审批的单据一个
    notifications: list[NotificationIntent]
    delivery_ids: list[str]
    prompts: list[Prompt]                        # C02 命令结果 prompts[] 的项
    skipped: list[SkippedRow]                    # C02 命令结果 skipped[] 的项
    pending_documents: set[DocumentRef]          # 提交审批的单据：本命令对这些单据的修改都不写业务表（approval AP-01）
    outcome: Literal["saved", "unchanged", "approvalSubmitted", "approvalProcessed"] | None   # 写入命令记录前由 write-pipeline 或触发审批阶段给出

@dataclass
class ChangePlan:
    rows: list[RowChange]

@dataclass
class RowChange:
    document: DocumentRef          # 所属单据；新增的单据在取得主键前，record_key 为主表行的 clientRowId
    entity: str
    op: Literal["add", "modify", "delete"]
    row_key: str | None            # 新增行在取得主键前为 None
    client_row_id: str | None
    values: dict[str, Value]       # 新增：要写入的字段；修改：有变化的字段的新值；删除：空
    old: dict[str, Value]          # 修改：这些字段的旧值；删除：删除前的整行（审计用）；新增：空
```

| 阶段 | 实现模块 | 读取 | 写入 |
|---|---|---|---|
| 操作权限 | authz | `command`、ctx | 无；不通过时抛 PERMISSION_DENIED |
| 确定涉及的单据 | write-pipeline、operations、approval | `command` | `involved`、`actions` |
| 冻结检查 | approval | `involved`、`command`、ctx | 无；命中时抛 FROZEN_BY_APPROVAL，ctx 来源为本审批时放行本审批的冻结 |
| 审批处理 | approval | `current`、`command` | `approvals`、`actions`、`notifications` |
| 动作执行 | operations、write-pipeline、authz、rules-core | `current`、`actions` | `candidate`、`effects`、`changes`、`prompts`、`skipped` |
| 触发审批 | approval | `effects`、`candidate`、`changes` | `approvals`、`pending_documents`、`outcome`、`notifications` |
| 登记通知 | delivery | `notifications` | `delivery_ids` |
| 投递 | delivery | `delivery_ids` | 无；提交后执行 |

判重、加锁并读取、写入变更、审计、写入命令记录并提交，由 write-pipeline 自己完成，不是可注册的阶段。

## 7. authz 提供

```python
class PermissionChecker(Protocol):
    def can_run(self, ctx: ExecutionContext, operation: str, page: str | None) -> bool: ...
    def row_condition(self, ctx: ExecutionContext, page: str, entity: str) -> SqlCondition | None: ...   # 没有行权限时为 None
    def writable_fields(self, ctx: ExecutionContext, page: str, entity: str) -> frozenset[str]: ...
    def can_export(self, ctx: ExecutionContext, page: str, export_code: str) -> bool: ...

@dataclass(frozen=True)
class SqlCondition:
    sql: str                       # 行权限的 SQL 条件，占位符已换成绑定变量名
    binds: dict[str, Value]        # 绑定变量的值
```

- 查询时，queries-export 把 `row_condition` 与筛选条件用 AND 组合。
- 写入时，write-pipeline 在加锁读取的同一条 SQL 中，把 `row_condition` 作为判断列一起查出，不另发 SQL；有一行超出范围就拒绝整个命令（403 PERMISSION_DENIED）。
- ctx 来源为审批时，写权限按操作声明的可写字段（C06）判断，不检查行权限和 `writable_fields`。

## 待确认

T-CT-3 编写替代实现和契约测试时发现的未定义行为。契约测试暂不检查这些行为；替代实现先按建议实现，确认后再补测试。

1. `ConfigSnapshot` 按编码取不存在的配置项。建议：`page_view` 对不存在的页面抛 404 NOT_FOUND，对该角色不能访问的页面抛 403 PERMISSION_DENIED，与 C09 的页面视图接口一致；`entity`、`operation`、`approval_flow`、`rules_pack` 取不到说明配置之间的引用断了（保存时已校验），抛 500 INTERNAL_ERROR。替代实现现在抛 KeyError。
2. `ConfigSnapshotReader.read` 收到的角色没有角色配置（例如角色已被删除）。建议抛 401 SESSION_ROLE_REVOKED，让用户重新选角色。替代实现现在抛 KeyError。
3. `ConfigImporter`：一批中有不合法的项时，建议整批都不导入，抛 422 VALIDATION_FAILED，明细列出每个不合法的项；已有同类型、同编码的配置项时，建议不覆盖，列入 `skipped`，这样重复导入不重复写入（T-MG-3）。替代实现现在整批不导入，但会覆盖已有的项。
4. 导入报告的计数和标识。建议：`imported` 为导入的主对象数：账号导入只数账号，配置导入数配置项，个人配置导入数（用户、页面）条目；`skipped` 的标识写成 `account:<userId>`、`config:<type>/<key>`、`personal:<userId>/<pageCode>`，原因用中文说明。
5. `PersonalConfigImporter` 遇到已有的个人配置。建议不覆盖，列入 `skipped`，与账号导入一致。
6. `RelatedQuery` 的 `rows` 为 `changed`（C06 7.2）：`find` 只收到来源单据，不知道哪些行是本次修改的。建议由调用方（approval、operations）处理：`rows` 为 `changed` 时，传入的 `source` 中明细只放本次修改了的来源行，主表行照常给出；端口签名不变。
7. 关联 SQL 的结果缺少 `recordKeyColumn` 时（queries-export 的 QE-08 写"报错"）。建议抛 500 INTERNAL_ERROR，不返回部分结果：保存时已校验，运行时缺列说明配置或表结构变了。
8. `RulesEngine.load_pack` 收到不合法的规则包（包括 C07 第 1 节的依赖成环）时，Python 中怎样表示 PACK_INVALID。建议在 contracts 中增加异常 `PackInvalidError(message)`，由 `load_pack` 抛出，消息列出环上的规则；config 保存时把它转成 422 VALIDATION_FAILED，启动预热时遇到它则启动失败（CF-13）。`evaluate` 收到不是本引擎加载的句柄时，按 C07 第 3 节返回 PACK_INVALID 的结果。
9. `DocumentReader.load_many` 中不存在的单据。建议不在结果中，与 `load` 返回 None 对应。替代实现已经这样做。
10. 契约测试的组织方式。建议写进第 14 节：每个端口的契约测试写成 `<端口名>Contract` 类，被测实现和准备数据的方法由 `harness` fixture 提供，接口写成同一文件中的 `<端口名>Harness` 协议；替代实现在同一文件中以 `TestFake<端口名>` 运行，真实实现在提供方的测试中继承同一个类，提供自己的 `harness`。只有提供方模块规则（例如 authz 的 AZ-01、config 的 CF-12）才有的行为，由提供方自己的测试验证，不放进契约测试。

以上确认后，第 14 节和各端口的注释按结论修改，C08 升为 v4。
