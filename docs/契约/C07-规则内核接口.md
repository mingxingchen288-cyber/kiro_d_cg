# C07 规则内核接口

版本：v4。维护：contracts。状态：已确认。v4 随 C06 v17（用户 2026-10-28 确认审批流的入口条件写 SQL）：审批条件不再由 rules-core 求值，去掉规则类别 `approvalTrigger`、规则包的 `approvalEntries`、求值目的 `approvalEntry` 和 `approve` 效果，由 C06 第 7 节推出。v3 写明 `packId`、计算规则的 JDM 写法和取值、删除行在请求中的表示（第 1、2 节），这几项属于实现细节，由实施者在 T-RC-2 中决定（架构第 5 节）。

rules-core 的 Python 包和 WASM 导出同样三个函数，后端经 `RulesEngine`（[C08](C08-后端端口.md)）调用，前端经计算 Worker（第 5 节）调用。

```
load_pack(pack_json: bytes) -> handle        同一规则包版本只编译一次
evaluate(handle, request_json: str) -> str   请求和结果都是 JSON 文本
core_version() -> str                        两个产物返回相同的值
```

## 1. 规则包

由 config 在保存配置时生成，按业务对象（主表实体及其明细）一份。

```json
{
  "packId": "COST_PINGGU",
  "version": 7,
  "coreVersion": "0.1.0",
  "fields": {
    "COST_PINGGU": {"QTY": {"type": "number", "scale": 2, "role": "input", "source": "own"}, "TOTAL_COST": {"type": "number", "scale": 2, "role": "calculated", "source": "own"}},
    "COST_MATERIAL": {"PRICE": {"type": "number", "scale": 4, "role": "input", "source": "own"}}
  },
  "rules": [
    {"id": "R_TOTAL", "layer": "entity", "entity": "COST_PINGGU", "category": "calc", "order": 10, "serverOnly": false, "jdm": "R_TOTAL"},
    {"id": "R_LOCK_PRICE", "layer": "page", "page": "COST_PINGGU", "category": "ui", "order": 200, "serverOnly": false, "jdm": "R_LOCK_PRICE"}
  ],
  "jdm": {"R_TOTAL": {"nodes": [], "edges": []}}
}
```

- `role`：`input`（输入）、`calculated`（计算）、`system`（系统）；`source`：`erp` 或 `own`。
- `layer`：`entity`（实体规则）、`operation`（操作规则）、`page`（页面规则，只管界面）；`category`：`calc`（计算）、`validate`（校验）、`ui`（界面）。审批流的入口条件是 SQL，由 approval 执行，不进规则包（C06 第 7 节）。
- `jdm` 由 config 按 C06 第 5 节的规则生成，用户不直接编辑；只允许五种节点：输入、输出、表达式、决策表、Switch，其他节点（包括函数节点）被拒绝。
- `serverOnly` 为 true 的规则依赖数据库数据，前端预览时不出结论。
- `rules` 中的顺序就是执行顺序，由 rules-core 在 `load_pack` 时按 C06 第 5 节算出；依赖成环时 `load_pack` 返回 `PACK_INVALID`，并列出环上的规则。
- `packId` 是主表实体的编码。
- 计算规则的 JDM 为输入、表达式、输出三个节点；表达式节点只有一个表达式，`key` 是规则作用的字段，`value` 是表达式。C06 第 5 节的 `when`、`branches` 编成一个条件表达式，按顺序取第一个成立的分支，都不成立时取字段自己（值不变），例如 `(w1) ? (e1) : ((w2) ? (e2) : 字段)`。
- 表达式中的取值：明细规则对每一行求值，本行字段直接写，主表字段写 `master.字段`；主表规则对单据求值一次，明细写明细实体的编码，值是这个明细的行的数组，例如 `sum(map(filter(COST_MATERIAL, #.DTL_USEFLAG == '原料'), #.COST_BATCH))`。另有 `old`、`context`、`data`。

## 2. 求值请求

```json
{
  "purpose": "operation",
  "operation": "COST_PINGGU.save",
  "page": "COST_PINGGU",
  "phase": "commit",
  "context": {"userId": "1", "departmentId": "10", "role": "COST_ACCOUNTANT", "today": "2026-10-24", "origin": "user"},
  "document": {
    "entity": "COST_PINGGU",
    "master": {"rowKey": "1001", "values": {"QTY": "10", "PRICE": "4.5"}},
    "details": {"COST_MATERIAL": [
      {"rowKey": "5001", "values": {"GOODSID": "115", "USAGE": "2", "PRICE": "3.50"}, "old": {"PRICE": "3.20"}},
      {"clientRowId": "tmp-6a1f2c3d-0b4e-4f5a-8c7d-9e0f1a2b3c4d", "values": {"GOODSID": "116", "USAGE": "1", "PRICE": "1.20"}}
    ]}
  },
  "changed": [{"entity": "COST_MATERIAL", "rowKey": "5001", "op": "modify", "fields": ["PRICE"]}],
  "data": {}
}
```

| 字段 | 说明 |
|---|---|
| `purpose` | 固定为 `operation`：计算和规则 |
| `phase` | `preview`：前端编辑时，执行实体、操作、页面三层规则；`commit`：后端写入前，只执行实体规则和操作规则 |
| `context.origin` | `user` 或 `approval` |
| `document` | 合并修改后的单据；数值都是十进制文本（C01）。已保存的行用 `rowKey`，新增行用 `clientRowId`，二者有且只有一个。修改过的行带 `old`，只列出改过的字段在本命令开始前的值；没有 `old` 的字段，旧值等于当前值；新增行没有 `old`，旧值为空 |
| `changed` | 本次修改的行和字段，规则据此判断"改了什么"；`op` 为 `delete` 的行是本次删除的行，仍放在 `document` 中，不计入主表的汇总 |
| `data` | 规则需要的数据库数据，由后端查出后填入；前端预览时为空 |

## 3. 求值结果

```json
{
  "ok": true,
  "rows": [
    {"entity": "COST_PINGGU", "rowKey": "1001", "computed": {"TOTAL_COST": "45.00"}, "fields": {"PRICE": {"editable": false}, "REMARK": {"required": true}}, "style": {"row": null, "cells": {}}}
  ],
  "effects": [
    {"kind": "prompt", "rule": "R_MARGIN_LOW", "message": "毛利率低于 5%", "entity": "COST_PINGGU", "rowKey": "1001", "field": "MARGIN"},
    {"kind": "reject", "rule": "R_PRICE_RANGE", "message": "价格超出范围", "entity": "COST_MATERIAL", "rowKey": "5001", "field": "PRICE"}
  ]
}
```

- 一次求值按 C06 第 5 节的执行顺序执行全部规则，给出全部计算字段的最终值；汇总包含新增行，不含标为删除的行。
- `computed` 不舍入，保留 rules-core 计算出的全部精度；保存时的小数位处理见 write-pipeline 的 WP-15。
- `effects[].kind`：`reject`（拒绝）、`prompt`（提示）。
- 行的定位：已保存的行用 `rowKey`，新增行用请求中的 `clientRowId`。`rows[]` 的每一项二者有且只有一个；`reject`、`prompt` 效果定位到行时二者给一个，只定位到单据时都省略。
- 除零、溢出、计算规则求值出错按 rules-core 模块说明第 8 节处理，不算出错。规则包或请求本身有问题时，返回 `{"ok": false, "error": {"code": "PACK_INVALID", "message": "…"}}`，`code` 取 `PACK_INVALID`、`INPUT_INVALID` 或 `EVAL_FAILED`；不返回部分结果，不含 panic 信息和调用栈。

## 4. 前后端的使用

- 两端加载同一版本的规则包，结果按 [C01](C01-数据格式.md) 第 3 节判定必须一致。
- 写入以后端 `commit` 阶段的结果为准；前端 `preview` 的结果只用于显示。

## 5. 前端 Worker 消息

```
主线程 → Worker：{"id": 1, "type": "load", "packId": "COST_PINGGU", "version": 7, "bytes": <ArrayBuffer>}
Worker → 主线程：{"id": 1, "ok": true, "handle": 3}
主线程 → Worker：{"id": 2, "type": "evaluate", "handle": 3, "request": "<第 2 节的 JSON 文本>"}
Worker → 主线程：{"id": 2, "ok": true, "result": "<第 3 节的 JSON 文本>"}
主线程 → Worker：{"type": "dispose", "handle": 3}
```

出错时 Worker 返回 `{"id": 2, "ok": false, "error": {"code": "…", "message": "…"}}`。

Worker 脚本、主线程客户端 `createCalcWorkerClient(wasmUrl): CalcWorkerClient`（C11）和 WASM 都由 rules-core 交付，放在 `rules-core/dist/web/`。Worker 内部调用 ES 模块 `index.js`（内含 WASI 适配），接口为：

```ts
export function init(wasmUrl: string): Promise<void>
export function loadPack(bytes: Uint8Array): number   // 返回句柄
export function evaluate(handle: number, request: string): string
export function dispose(handle: number): void
export function coreVersion(): string
```

Python 包中的句柄由垃圾回收释放，没有 `dispose`。

## 6. 契约测试

- rules-core 的样例集（`rules-core/fixtures/` 下成对的请求和期望结果）在 Python 包和 WASM 上都运行，结果按 C01 第 3 节判定一致。
- 两个产物的 `core_version()` 相同。
