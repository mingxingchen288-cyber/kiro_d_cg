# C07 规则内核接口

版本：v8。维护：contracts。状态：v4 已确认；v5、v6、v7、v8 待用户审核。v8 由 v7 与 WP-15 的衔接推出（实施者决定）：判断计算带出变化时，算出的数值先按 write-pipeline WP-15 的写法（最多 8 位小数，第 9 位四舍五入，负数按绝对值）处理成保存后的值，再与 `old` 比较；计算本身和 `computed` 仍不舍入（第 3 节）。原因：计算不舍入（RC-04），库里存的最多 8 位小数，算出超过 8 位小数的行（例如 2 × 18.3333333333 = 36.6666666666，库里是 36.66666667）每次重算都与 `old` 不同，被当成有修改去校验，后端按 8 位处理后相同、不会写它；旧系统按字段精度舍入，存的就是算出的值，重算没有变化。列定义了小于 8 的小数位时 WP-15 按列处理，rules-core 不知道列的小数位（规则包字段的 `scale` 是显示小数位，C05），这里一律按 8 位；d_cg 和旧库 cmx 中计算字段的列都没有定义小数位，按 8 位与后端相同。v7 由旧系统计算带出的修改推出（`cost-web/src/v3/composables/meta-v3/useCalcBroadcast.ts` 第 382、418、466、548、565 行：明细自身计算、主表自身计算、主表改了广播到每行明细、明细汇总到主表、汇总后主表再计算，算出的值与当前值不同时都用 `markFieldChange(…, 'calc')` 记成修改；`useWorkingSetStore.ts` 第 178–196 行：新值等于原值时去掉这一列，行没有列了就不算修改；第 886–934 行：保存时校验有修改、没有删除的主表行和明细行）：校验规则检查的行改为 `changed` 中新增、修改的行，加上本次计算后有计算字段的值与 `old` 不同的行（第 2 节 `changed`、第 3 节）。例如改了主表批量，每批数量因此变化的原辅料行都要校验；改了明细单价，主表汇总变了，主表也要校验。由实施者决定的：数值按 C01 第 3 节判定一致即视为没有变化。v6 由旧系统表格的行样式推出（`cost-web/src/v3/composables/meta-v3/usePageRules.ts` 的 `buildRowStyleCallback`：GRID_STYLE 作为 AG Grid 的 `getRowStyle`，渲染行时按行数据算样式，页面加载即显示，不需要编辑；可编辑规则同样是按行数据判断的回调）：求值请求增加 `purpose: "display"`，只执行界面规则，不计算、不校验，供前端在页面一显示时使用（第 3.1 节）。由实施者决定的：用 `purpose` 区分而不是另加函数（三个函数和 Worker 消息不变）；主表列表中没加载明细时，引用明细的主表界面规则不出结论。v5 由旧系统保存时的校验推出（`cost-web/src/v3/composables/meta-v3/useWorkingSetStore.ts` 第 886–934 行：只收集有修改的主表行和明细行，去掉删除的行后校验，主表没有修改时不校验主表）：校验规则只检查 `changed` 中本次新增、修改的行（v7 起加上计算带出变化的行），主表行也一样，删除的行不检查；计算规则和界面规则照常对全部行执行（第 2 节 `changed`、第 3 节）。v4 随 C06 v17（用户 2026-10-28 确认审批流的入口条件写 SQL）：审批条件不再由 rules-core 求值，去掉规则类别 `approvalTrigger`、规则包的 `approvalEntries`、求值目的 `approvalEntry` 和 `approve` 效果，由 C06 第 7 节推出。v3 写明 `packId`、计算规则的 JDM 写法和取值、删除行在请求中的表示（第 1、2 节），这几项属于实现细节，由实施者在 T-RC-2 中决定（架构第 5 节）。

rules-core 的 Python 包和 WASM 导出同样三个函数，后端经 `RulesEngine`（[C08](C08-后端端口.md)）调用，前端经计算 Worker（第 5 节）调用。

```
load_pack(pack_json: bytes) -> handle        同一规则包版本只编译一次
evaluate(handle, request_json: str) -> str   请求和结果都是 JSON 文本
core_version() -> str                        两个产物返回相同的值
```

## 1. 规则包

由 config 在保存配置时生成，按业务对象（主表实体及其明细）一份。

```json
{
  "packId": "COST_PINGGU",
  "version": 7,
  "coreVersion": "0.1.0",
  "fields": {
    "COST_PINGGU": {"QTY": {"type": "number", "scale": 2, "role": "input", "source": "own"}, "TOTAL_COST": {"type": "number", "scale": 2, "role": "calculated", "source": "own"}},
    "COST_MATERIAL": {"PRICE": {"type": "number", "scale": 4, "role": "input", "source": "own"}}
  },
  "rules": [
    {"id": "R_TOTAL", "layer": "entity", "entity": "COST_PINGGU", "category": "calc", "order": 10, "serverOnly": false, "jdm": "R_TOTAL"},
    {"id": "R_LOCK_PRICE", "layer": "page", "page": "COST_PINGGU", "category": "ui", "order": 200, "serverOnly": false, "jdm": "R_LOCK_PRICE"}
  ],
  "jdm": {"R_TOTAL": {"nodes": [], "edges": []}}
}
```

- `role`：`input`（输入）、`calculated`（计算）、`system`（系统）；`source`：`erp` 或 `own`。
- `layer`：`entity`（实体规则）、`operation`（操作规则）、`page`（页面规则，只管界面）；`category`：`calc`（计算）、`validate`（校验）、`ui`（界面）。审批流的入口条件是 SQL，由 approval 执行，不进规则包（C06 第 7 节）。
- `jdm` 由 config 按 C06 第 5 节的规则生成，用户不直接编辑；只允许五种节点：输入、输出、表达式、决策表、Switch，其他节点（包括函数节点）被拒绝。
- `serverOnly` 为 true 的规则依赖数据库数据，前端预览时不出结论。
- `rules` 中的顺序就是执行顺序，由 rules-core 在 `load_pack` 时按 C06 第 5 节算出；依赖成环时 `load_pack` 返回 `PACK_INVALID`，并列出环上的规则。
- `packId` 是主表实体的编码。
- 计算规则的 JDM 为输入、表达式、输出三个节点；表达式节点只有一个表达式，`key` 是规则作用的字段，`value` 是表达式。C06 第 5 节的 `when`、`branches` 编成一个条件表达式，按顺序取第一个成立的分支，都不成立时取字段自己（值不变），例如 `(w1) ? (e1) : ((w2) ? (e2) : 字段)`。
- 表达式中的取值：明细规则对每一行求值，本行字段直接写，主表字段写 `master.字段`；主表规则对单据求值一次，明细写明细实体的编码，值是这个明细的行的数组，例如 `sum(map(filter(COST_MATERIAL, #.DTL_USEFLAG == '原料'), #.COST_BATCH))`。另有 `old`、`context`、`data`。

## 2. 求值请求

```json
{
  "purpose": "operation",
  "operation": "COST_PINGGU.save",
  "page": "COST_PINGGU",
  "phase": "commit",
  "context": {"userId": "1", "departmentId": "10", "role": "COST_ACCOUNTANT", "today": "2026-10-24", "origin": "user"},
  "document": {
    "entity": "COST_PINGGU",
    "master": {"rowKey": "1001", "values": {"QTY": "10", "PRICE": "4.5"}},
    "details": {"COST_MATERIAL": [
      {"rowKey": "5001", "values": {"GOODSID": "115", "USAGE": "2", "PRICE": "3.50"}, "old": {"PRICE": "3.20"}},
      {"clientRowId": "tmp-6a1f2c3d-0b4e-4f5a-8c7d-9e0f1a2b3c4d", "values": {"GOODSID": "116", "USAGE": "1", "PRICE": "1.20"}}
    ]}
  },
  "changed": [{"entity": "COST_MATERIAL", "rowKey": "5001", "op": "modify", "fields": ["PRICE"]}],
  "data": {}
}
```

| 字段 | 说明 |
|---|---|
| `purpose` | `operation`：计算和规则；`display`：只执行界面规则，前端页面一显示就用（第 3.1 节） |
| `phase` | `preview`：前端编辑时，执行实体、操作、页面三层规则；`commit`：后端写入前，只执行实体规则和操作规则 |
| `context.origin` | `user` 或 `approval` |
| `document` | 合并修改后的单据；数值都是十进制文本（C01）。已保存的行用 `rowKey`，新增行用 `clientRowId`，二者有且只有一个。修改过的行带 `old`，只列出改过的字段在本命令开始前的值；没有 `old` 的字段，旧值等于当前值；新增行没有 `old`，旧值为空 |
| `changed` | 本次修改的行和字段，规则据此判断"改了什么"；`op` 为 `delete` 的行是本次删除的行，仍放在 `document` 中，不计入主表的汇总。后端 commit 时为页面保存新增、修改的行和按钮动作新增、修改的行（write-pipeline 的变更计划），前端 preview 时为当前单据有修改的行。校验规则检查这里 `op` 为 `add`、`modify` 的行，以及计算带出变化的行（v7，第 3 节）；计算带出的变化由 rules-core 按 `old` 判断，不需要列在这里 |
| `data` | 规则需要的数据库数据，由后端查出后填入；前端预览时为空 |

## 3. 求值结果

```json
{
  "ok": true,
  "rows": [
    {"entity": "COST_PINGGU", "rowKey": "1001", "computed": {"TOTAL_COST": "45.00"}, "fields": {"PRICE": {"editable": false}, "REMARK": {"required": true}}, "style": {"row": null, "cells": {}}}
  ],
  "effects": [
    {"kind": "prompt", "rule": "R_MARGIN_LOW", "message": "毛利率低于 5%", "entity": "COST_PINGGU", "rowKey": "1001", "field": "MARGIN"},
    {"kind": "reject", "rule": "R_PRICE_RANGE", "message": "价格超出范围", "entity": "COST_MATERIAL", "rowKey": "5001", "field": "PRICE"}
  ]
}
```

- 一次求值按 C06 第 5 节的执行顺序执行全部规则，给出全部计算字段的最终值；汇总包含新增行，不含标为删除的行。
- 校验规则只对有修改的行执行，`reject`、`prompt` 只会定位到这些行（或它们所在的单据）。有修改的行（v7）= `changed` 中新增、修改的行 ∪ 本次计算后有计算字段的值与 `old`（本命令开始前的值；没有 `old` 的字段等于请求中的当前值，新增行为空）不同的行；数值按 C01 第 3 节判定一致即视为没有变化，一方为空、另一方为数值时算有变化；删除的行不检查。主表行同样：本次没有修改、汇总也没有变化时，不执行主表的校验规则。计算规则和界面规则对全部行执行。
- 比较时算出的数值先按 WP-15 处理成保存后的值（v8）：最多 8 位小数，第 9 位四舍五入，负数按绝对值四舍五入；`old` 不处理（旧系统按浮点写入的值，例如 16326.530612244898，与保存后的 16326.53061224 不同，后端会写入新值，算作变化）。列定义了小于 8 的小数位时，WP-15 按列的小数位处理，rules-core 不知道列的小数位，这里仍按 8 位；d_cg 和旧库 cmx 的成本核算主表、明细表和物料表中，计算字段的列都没有定义小数位（`NUMBER`），定义了小数位的只有主键、外键和标记列（`NUMBER(p,0)`，不是计算字段），两者相同。
  - 成本单 2712 的明胶空心胶囊若每片含量为 0、单价为 18.3333333333（都是假设；这个单价是 d_cg 单据 2757 乙醇的真实单价），每批数量 2，每批成本算出 36.6666666666，库里存的是 36.66666667：只改硬脂酸镁的单价时，胶囊这一行按保存后的值没有变化，不检查，能保存；v7 时每次都被它拒绝"每片含量必填且必须大于0"。
  - 成本单 2757 的原辅料"30%过氧化氢溶液"每片含量为 0：只改硬脂酸镁的单价时，它的每批数量、每批成本都没有变化，不检查，能保存；改它自己的单价时被拒绝"每片含量必填且必须大于0"。把批量 1600000 改成 1700000 时，它的每批数量 = 0 × 批量仍是 0，也不检查，能保存；其余 8 行原辅料的每批数量变了，都检查并通过。
  - 名称含"胶囊"的原辅料每批数量按批量算，不看每片含量（`R_MAT_BATCH_QTY` 第一个分支）。成本单 2712（100mg消旋卡多曲胶囊）的明胶空心胶囊若每片含量为 0（假设；d_cg 中是 100，d_cg 没有每片含量不大于 0 的胶囊行），批量 20000 改成 30000 后它的每批数量 2 → 3，这一行有修改，被拒绝"每片含量必填且必须大于0"。
- `computed` 不舍入，保留 rules-core 计算出的全部精度；保存时的小数位处理见 write-pipeline 的 WP-15。WP-15 的写法只用于判断计算是否带出变化（上一条），不改变 `computed`。
- `effects[].kind`：`reject`（拒绝）、`prompt`（提示）。
- 行的定位：已保存的行用 `rowKey`，新增行用请求中的 `clientRowId`。`rows[]` 的每一项二者有且只有一个；`reject`、`prompt` 效果定位到行时二者给一个，只定位到单据时都省略。
- 除零、溢出、计算规则求值出错按 rules-core 模块说明第 8 节处理，不算出错。规则包或请求本身有问题时，返回 `{"ok": false, "error": {"code": "PACK_INVALID", "message": "…"}}`，`code` 取 `PACK_INVALID`、`INPUT_INVALID` 或 `EVAL_FAILED`；不返回部分结果，不含 panic 信息和调用栈。

### 3.1 显示求值（`purpose` 为 `display`，v6）

旧系统的行样式在表格渲染行时按行数据计算（GRID_STYLE 的 `getRowStyle`），页面一加载就显示，不需要先编辑。新平台的前端在主表一块数据取到时、一张单据的明细加载时，对这些行做一次显示求值，得到界面规则的样式、可编辑和必填；单据有修改后改用 preview 的结果。

- 请求格式同第 2 节：`phase` 必须是 `preview`（否则 `INPUT_INVALID`），`changed` 为空数组，`data` 为空；行的值取当前显示的值（没有修改的行就是加载来的值），不带 `old`。
- 只执行 preview 阶段会选中的界面规则（`category` 为 `ui`，实体、操作、页面三层，`serverOnly` 的不执行），不执行计算规则和校验规则。行的值按请求原样参与条件，不重算计算字段。
- 主表列表中只有主表行、没有加载明细时，`document.details` 为空对象：条件引用了请求中没有给出的明细的主表界面规则，这次不出结论（同 `serverOnly` 在 preview 中不出结论）；给出了明细（行可以为空数组）时照常执行。
- 结果格式同第 3 节：`rows` 给出请求中每一行的 `fields`、`style`，`computed` 为空对象；`effects` 为空数组。

例：成本核算主表列表中的 d_cg 单据 2919（比沙可啶肠溶片），MEMO 为"ERP未搭建BOM"，不编辑就整行红底；主表的计算字段照数据库的值显示（TOTAL_COST 在 d_cg 中为 0，显示求值不重算）。

```json
{
  "purpose": "display",
  "operation": "COST_PINGGU.save",
  "page": "COST_PINGGU",
  "phase": "preview",
  "context": {"userId": "1", "departmentId": "10", "role": "COST_ACCOUNTANT", "today": "2026-10-30", "origin": "user"},
  "document": {
    "entity": "COST_PINGGU",
    "master": {"rowKey": "2919", "values": {"GOODSNAME": "比沙可啶肠溶片", "MEMO": "ERP未搭建BOM", "APEX_PL": "850000", "TOTAL_COST": "0"}},
    "details": {}
  },
  "changed": [],
  "data": {}
}
```

    {"entity": "COST_PINGGU", "rowKey": "2919", "computed": {}, "fields": {}, "style": {"row": {"backgroundColor": "#ffcccc"}, "cells": {}}}

## 4. 前后端的使用

- 两端加载同一版本的规则包，结果按 [C01](C01-数据格式.md) 第 3 节判定必须一致。
- 写入以后端 `commit` 阶段的结果为准；前端 `preview` 和 `display` 的结果只用于显示。后端不发 `display` 请求。

## 5. 前端 Worker 消息

```
主线程 → Worker：{"id": 1, "type": "load", "packId": "COST_PINGGU", "version": 7, "bytes": <ArrayBuffer>}
Worker → 主线程：{"id": 1, "ok": true, "handle": 3}
主线程 → Worker：{"id": 2, "type": "evaluate", "handle": 3, "request": "<第 2 节的 JSON 文本>"}
Worker → 主线程：{"id": 2, "ok": true, "result": "<第 3 节的 JSON 文本>"}
主线程 → Worker：{"type": "dispose", "handle": 3}
```

出错时 Worker 返回 `{"id": 2, "ok": false, "error": {"code": "…", "message": "…"}}`。

Worker 脚本、主线程客户端 `createCalcWorkerClient(wasmUrl): CalcWorkerClient`（C11）和 WASM 都由 rules-core 交付，放在 `rules-core/dist/web/`。Worker 内部调用 ES 模块 `index.js`（内含 WASI 适配），接口为：

```ts
export function init(wasmUrl: string): Promise<void>
export function loadPack(bytes: Uint8Array): number   // 返回句柄
export function evaluate(handle: number, request: string): string
export function dispose(handle: number): void
export function coreVersion(): string
```

Python 包中的句柄由垃圾回收释放，没有 `dispose`。
