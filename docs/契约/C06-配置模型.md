# C06 配置模型

版本：v10。维护：contracts。状态：已确认。

配置存在数据库中，每个配置项只有当前版本，没有草稿。管理员在 frontend-config 中编辑，经 `PUT /api/config/items/{type}/{key}`（[C09](C09-HTTP接口.md)）保存；config 校验通过后保存即生效。migration 经 `ConfigImporter`（[C08](C08-后端端口.md)）写入，校验规则相同。

## 1. 配置项

```json
{"type": "page", "key": "COST_PINGGU", "name": "成本核算", "version": 13, "updatedBy": "1", "updatedAt": "2026-10-24T10:00:00", "content": {}}
```

| `type` | `content` 见 | 说明 |
|---|---|---|
| `entity` | 第 2 节 | 实体与表、字段的对应 |
| `page` | 第 3 节 | 页面，含字段设置和表单布局 |
| `operation` | 第 4 节 | 页面保存、按钮操作 |
| `rule` | 第 5 节 | 计算、校验和界面规则 |
| `approvalFlow` | 第 7 节 | 审批流，含触发条件、关联对象、冻结、展示内容和批准后动作 |
| `role` | 第 8 节 | 角色及其页面、操作、行和字段权限 |
| `menu`、`dict`、`lookup`、`export` | 第 9 节 | 菜单、字典、Lookup、导出 |

`version` 每次保存加一。

### 1.1 字段的省略

`content` 中的字段按以下规则读取，config 保存和 migration 导入相同；字段的值照常按 C01 的格式。

- 下表没有列出的字段都必须写出；值可以为 null 的字段，没有值时写 null。
- 决定行为的字段必须明确写出，平台不补默认值：page 的 `audit`、`detailMode`，operation 的 `propagation`，rule 的 `order`，approvalFlow 的 `trigger.changedFields`、`params[].required`，role 的 `admin`，dict 的 `items[].order`，lookup 的 `keywordColumns`。配置界面可以预填这些字段，但保存时必须带上。
- 下表中省略时为"空"的是数组或对象，省略等于写出空数组或空对象。
- 省略时为"无"的是可选的单个值，省略表示没有设置这一项，含义见各字段的说明。对象类型的可选字段也是这样，例如 page 字段的 `lookup.filter` 省略表示不筛选，不等于空对象 `{}`。
- 省略时为具体值的，是字段自己的默认值，优先于上面两条。例如 `trigger.operations` 省略时为 `["modify"]`，写出空数组则保存被拒绝（第 10 节）。

| 结构 | 可以省略的字段：省略时 |
|---|---|
| `entity` 的内容 | `readView`、`erpRow`：无；`details`、`fieldDefaults`、`approvalRequired`：空 |
| entity 的 `fields[]` | `scale`、`default`、`compare`：无 |
| entity 的 `approvalRequired[]` | `when`：无 |
| `approvalRequired[].when.conditions[]` | `value`：无 |
| 字段的可见、可编辑、必填（entity 的 `fieldDefaults`，role 的 `columns`） | `visible`、`editable`、`required`：无 |
| `page` 的内容 | `details`：空 |
| page 的 `master`、`details[]` | `fields`、`buttons`、`formLayout`：空 |
| page 区域 `fields` 中的每个字段 | `visible`、`editable`、`required`、`width`、`pinned`、`dictType`、`lookup`：无 |
| page 字段的 `lookup` | `multiple`：`false`；`filter`：无；`fillBack`：`true` |
| page 字段的 `lookup.filter` | `field`：无 |
| page 区域的 `buttons[]` | `operation`、`requiresSelection`：无 |
| `operation` 的内容 | `writableFields`、`impact`、`actions`、`writes`：空；`procedure`：无；`rowNotFound`：`"skip"` |
| `updateTargets` 的 `targets[]` | `detailEntity`：无；`match`：空 |
| 关联 SQL（7.2，也用于 `freeze` 和 `updateRecords`） | `binds`、`rowKeyColumns`、`displayColumns`：空；`labelColumn`：无 |
| `rule` 的内容 | `field`、`when`、`expression`、`branches`、`level`、`message`、`effect`：无；`dataItems`：空 |
| 可视化条件的 `conditions[]`（第 5 节） | `value`：无 |
| rule 的 `branches[]` | `when`：无 |
| rule 的 `effect` | `editable`、`required`、`rowStyle`、`cellStyle`：无 |
| `dataItems[]` | `binds`：空 |
| approvalFlow 的 `trigger` | `operations`：`["modify"]`；`dataItems`：空；`when`：无 |
| approvalFlow 的 `levels[].entries[]` | `when`：无 |
| SQL 审批人 | `binds`：空 |
| `approvalFlow` 的内容 | `targets`、`display`：无；`freeze`、`afterApproval`、`params`、`notify`：空；`propagation`：`"end"` |
| approvalFlow 的 `params[]` | `level`、`value`：无 |
| approvalFlow 的 `display` | `details`：空 |
| `display.master` | `columns`：空 |
| `display.details[]` | `rowsFilter`：`"changed"`；`columns`：空 |
| `role` 的内容 | `pages`：空 |
| role `pages` 中的每个页面 | `buttons`、`columns`：空；`rows`：无 |
| 行权限可视化条件的 `conditions[]`（第 8 节） | `value`：无 |
| menu 的 `items[]`（含 `children`） | `pageCode`：无；`children`：空 |
| `lookup` 的内容 | `orderBy`：无 |
| `export` 的内容 | `font`：`"Calibri"`；`detailLayout`：`"perMaster"`；`details`：空 |

## 2. entity

```json
{
  "table": "T_COST_PINGGU",
  "primaryKey": "DOCID",
  "freezable": true,
  "fields": [
    {"name": "DOCID", "column": "DOCID", "label": "单据号", "type": "number", "scale": 0, "source": "own", "role": "system"},
    {"name": "GOODSNAME", "column": "GOODSNAME", "label": "产品名称", "type": "text", "source": "erp", "role": "input"},
    {"name": "TOTAL_COST", "column": "TOTAL_COST", "label": "总成本", "type": "number", "scale": 2, "source": "own", "role": "calculated"}
  ],
  "details": [{"entity": "COST_MATERIAL", "parentKey": "DOCID"}],
  "fieldDefaults": {"TOTAL_COST": {"visible": true, "editable": false, "required": false}}
}
```

- `source`：`erp` 为 ERP 列，由 ERP 同步写入；`own` 为平台自有列。
- `erpRow`：可选，标识哪些行来自 ERP，例如物料表 `{"column": "ISERP", "value": "1", "localValue": "0"}`。
  - 没有 `erpRow` 的实体，ERP 列在所有行上都只读，任何操作都不能写。
  - 有 `erpRow` 的实体，ERP 列只在 ERP 行（该列等于 `value`）上只读；本地行和新增行（含复制出的行）的 ERP 列由平台维护，按页面和角色设置判断能否编辑。
  - `column` 本身只由平台写：新增和复制的行由平台设为 `localValue`，不从源行复制，用户不能修改。
- `role`：`input`、`calculated`（由规则计算，用户不能输入）、`system`（主键等）。
- `freezable`：是否可被审批冻结；为 false 的实体，写入时不做冻结检查，也不能作为审批流的来源单据或锁定对象（第 10 节）。
- `approvalRequired`：可选，必须审批的字段规则，对应旧系统的 `APPROVAL_REQUIRED`。例如物料表 `[{"fields": ["ZX_PRICE"], "when": {"logic": "AND", "conditions": [{"field": "ISERP", "op": "eq", "value": "1"}]}, "sourcePages": ["GOODS_PRICE_MANAGE"]}]`。
  - `when` 只用本行字段，`op` 取 `eq`、`ne`、`isNull`、`isNotNull`，不能用 SQL；修改前或修改后的行满足 `when` 都算命中；省略 `when` 时所有行都满足。
  - 命中条件：修改了 `fields` 中的字段，或者删除了满足 `when` 的行，或者新增了满足 `when` 且填写了 `fields` 的行。
  - 规则属于实体，与页面和审批流无关：任何写入口写这个实体都检查，停用或删除审批流不会让规则失效。处理见 approval 的 AP-18。
- `fields[].column` 为 null 时，字段只存在于 `readView` 中，只读显示，不写入。从视图导入列时，表中没有的列按这种方式生成。
- `fields[].default`：新增行的默认值，与旧系统相同，有三种写法：
  - `{"type": "static", "value": "1"}`：固定值；
  - `{"type": "builtin", "value": "currentUserId"}`：取值 `currentUserId`、`currentUserName`、`currentDeptId`、`currentDeptName`、`currentRoleCode`、`currentTime`（日期字段取当天，日期时间字段取当前时间）；
  - `{"type": "options", "value": ["A", "B"]}`：单元格用下拉选择这些值，新增行默认取第一个。
  - 没有配置时，数值字段默认为 0，其他字段为空，与旧系统相同。赋值时机见 write-pipeline 的 WP-16。
- `fields[].compare`：可选，与历史或关联数据对比，对应旧系统的 `rulesConfig.compare`：
  - `{"mode": "field", "field": "LAST_PRICE", "format": "both"}`：与同一行的另一个字段对比；
  - `{"mode": "query", "source": "T_COST_GOODS_HIS_V", "keys": [{"current": "GOODSID", "compare": "GOODSID"}], "field": "PRICE", "format": "percent"}`：按关联键到另一个表或视图取对比值；
  - `format` 取 `value`（差值）、`percent`（百分比）、`both`。结果只用于显示，见 queries-export 的 QE-10。
- 新增行的主键取序列 `<表名>_SEQ` 的下一个值，例如 `T_COST_PINGGU` 用 `T_COST_PINGGU_SEQ`。
- `readView`：可选的视图名。设置后，列表、单据加载、审批详情，以及写入管道加锁读取当前值，都经这个视图读取；写入仍写到 `table` 的同名列。视图只能基于这一张表，必须包含主键和实体的全部字段。例如物料清单用 `T_COST_GOODS_PRICE_V`：视图过滤掉了"产成品""半成品"，视图中的 `ZX_PRICE` 在表中的 ZX_PRICE 为空时取 PRICE。

## 3. page

```json
{
  "title": "成本核算",
  "layout": "masterDetail",
  "detailMode": "tabs",
  "audit": true,
  "saveOperation": "COST_PINGGU.save",
  "master": {
    "entity": "COST_PINGGU",
    "fields": {"PRICE": {"editable": false}, "DOCID": {"width": 120, "pinned": "left"}},
    "buttons": [{"action": "addRow", "label": "新增"}, {"action": "copyRow", "label": "复制"}, {"action": "deleteRow", "label": "删除"}, {"action": "syncPrice", "label": "同步价格", "operation": "COST_PINGGU.syncPrice", "requiresSelection": true}, {"action": "saveGridConfig", "label": "保存列配置"}], "grid": {"sideBar": true, "cellSelection": true, "groupBy": []},
    "formLayout": [{"field": "GOODSNAME", "x": 0, "y": 0, "w": 12, "h": 1}]
  },
  "details": [
    {"entity": "COST_MATERIAL", "title": "材料", "fields": {}, "buttons": [{"action": "addRow", "label": "新增"}, {"action": "copyRow", "label": "复制"}, {"action": "deleteRow", "label": "删除"}], "grid": {"sideBar": true, "cellSelection": true, "groupBy": []}, "formLayout": []}
  ]
}
```

- `layout` 为 `single` 时是单表页，`details` 为空。
- `audit`：本页面的命令是否记录审计差异（write-pipeline 的 WP-11）；`detailMode`：明细的默认显示方式，`tabs` 或 `stack`。两项都必须写，单表页也要写 `detailMode`（第 1.1 节）。
- `fields` 中只写本页面要改的设置：`visible`、`editable` 只能收紧，`required` 只能加；另可设 `width`、`pinned`、`dictType`、`lookup`。
- `lookup` 的写法：`{"code": "GOODS", "fill": {"GOODSID": "GOODSID", "GOODSNAME": "NAME"}, "multiple": false, "filter": {"column": "GOODSTYPE", "from": "row", "field": "PACKTYPE"}, "fillBack": true}`，对应旧系统的 Lookup 规则：
  - `multiple` 为 true 时可以选多行，同一个回填字段的值用英文逗号连接；省略时为 false；
  - `filter` 只查 `column` 等于某个值的行，值取当前行的 `field`（`from` 为 `row`），或者取点开的单元格的值（`from` 为 `cell`，不用 `field`）；值为空时不过滤；省略 `filter` 表示不筛选；
  - `fillBack` 为 false 时只查看、不回填，只读的单元格也可以打开；省略时为 true。
  - 这三项省略时的值与 C05 页面视图相同。
- `formLayout` 由管理员拖动编辑，所有人共用。
- `buttons`：本区域工具栏和右键菜单中的按钮，格式同旧系统的组件按钮。`action` 为内置动作 `addRow`（新增）、`copyRow`（复制）、`deleteRow`（删除）、`saveGridConfig`（保存列配置），或业务动作；业务动作用 `operation` 引用操作库中的操作，并且必须写 `requiresSelection`：为 true 时没有选中行就不可用，后端也检查（operations 的 OP-05）。`requiresSelection` 只规定执行的前提，实际处理的行和权限仍由后端检查（OP-05）。内置动作不写 `operation` 和 `requiresSelection`，是否需要选中行由平台统一规定，见 config 的 CF-03。保存、高级查询是页面级按钮，不用写在区域里。
- 按钮显示出来还要角色有权限，见第 8 节。

## 4. operation

```json
{
  "label": "保存",
  "kind": "save",
  "writableFields": {"COST_PINGGU": ["QTY", "REMARK"], "COST_MATERIAL": ["GOODSID", "USAGE", "PRICE"]},
  "impact": ["COST_PINGGU", "COST_MATERIAL"],
  "actions": [],
  "rowNotFound": "skip",
  "propagation": "continue"
}
```

| 字段 | 说明 |
|---|---|
| `kind` | `save`：页面保存，修改来自 Patch；`action`：按钮，按 `actions` 执行；`escapeHatch`：逃生舱，只在用户点名时启用 |
| `writableFields` | 本操作允许写入的字段。审批的批准后动作按这里判断写权限，不按个人权限 |
| `impact` | 本操作可能修改的实体，用于返回受影响行 |
| `actions` | `kind` 为 `action` 时的通用动作，见第 6 节 |
| `rowNotFound` | 要修改或删除的行已被删除时（按钮操作为选中的行，C02 第 1 节）：`skip`（默认，跳过并提示）或 `reject` |
| `propagation` | `continue` 或 `end`，必须写；为 `end` 时，本操作写到的目标不再触发审批和同步 |
| `procedure`、`writes` | 只用于 `escapeHatch`：登记调用的存储过程和会修改的表、列，不能包含 ERP 列 |

## 5. rule

规则和旧系统一样按表单编辑，保存在配置中，不需要图形编辑器。config 保存时把每条规则转成 JDM（只用输入、表达式、输出节点），编进规则包（[C07](C07-规则内核接口.md)）；用户不直接编辑 JDM。

计算规则（包材明细的批量，按物料名称分两种算法）：

```json
{"layer": "entity", "target": "COST_PACKAGE", "category": "calc", "field": "BATCH_QTY", "order": 10, "dataItems": [],
 "branches": [
  {"when": "matches(GOODSNAME, '桶|说明书|小盒|标签|瓶|盖|干燥剂|序列化')", "expression": "master.APEX_PL / master.P_PERPACK * (1 + EXADD_MATER / 100)"},
  {"when": "matches(GOODSNAME, '硬片|铝箔|复合膜')", "expression": "PER_HL * master.APEX_PL * (1 + EXADD_MATER / 100) / 1000000"}]}
```

界面规则（ERP 来的物料整行不能编辑，条件用可视化写法）：

```json
{"layer": "page", "target": "GOODS_MANAGE", "category": "ui", "field": null, "order": 10,
 "when": {"logic": "AND", "conditions": [{"source": "row", "field": "ISERP", "op": "eq", "value": "1"}]},
 "effect": {"editable": false}}
```

| 字段 | 说明 |
|---|---|
| `layer` | `entity`：写到该实体时都执行；`operation`：执行该操作时执行；`page`：只管界面，只在前端预览时执行 |
| `target` | 实体编码、操作编码或页面编码 |
| `category` | `calc`：计算字段的值；`validate`：校验；`ui`：可编辑、必填和样式 |
| `field` | 规则作用的字段，属于规则所在的实体（主表或某个明细）。`calc` 必填；`ui` 为空时作用于整行 |
| `when` | 条件：表达式文本，或可视化条件（`logic` 为 `AND` 或 `OR`；`conditions` 每项含 `source`（`row` 本行、`master` 主表）、`field`、`op`、`value`，`op` 的取值同第 8 节）。为空表示总是成立 |
| `expression`、`branches` | `calc` 的计算表达式；分情况计算时用 `branches`，按顺序取第一个 `when` 成立的分支，都不成立时字段值不变 |
| `level`、`message` | `validate`：`when` 成立时给出 `reject`（拒绝保存）或 `prompt`（提示）和提示文字 |
| `effect` | `ui`：`when` 成立时生效，可含 `editable`、`required`、`rowStyle`、`cellStyle` |
| `order` | 整数，必须写；只在两条规则之间没有依赖关系时决定先后，执行顺序见下面的规定 |
| `dataItems` | 规则需要的数据库数据：`[{"name": "usage", "sql": "SELECT … WHERE GOODSID = :goodsId", "binds": {"goodsId": "GOODSID"}}]`，表达式中写作 `data.usage`。有数据项的规则只在后端执行 |

表达式使用 ZEN 表达式语法，数值按十进制计算，不经过浮点。取值约定：

- 作用字段属于主表时，表达式对每张单据求值一次：主表字段直接写字段名；明细写明细实体编码，值是行的数组，例如 `sum(map(COST_MATERIAL, #.USAGE * #.PRICE))`。
- 作用字段属于明细时，表达式对该明细的每一行求值一次：本行字段直接写字段名，主表字段写 `master.字段`。
- `old.字段` 是本命令开始前的正式值：后端取加锁读取时读到的当前值，前端取从后端加载到的值，都不另查数据库；新增行为空；本次没有修改的字段，`old` 与当前值相同。`context.userId`、`context.role`、`context.today` 取执行上下文。
- 审批流的 `trigger.when` 和入口的 `when`（第 7 节）按主表的约定求值。

执行顺序：

1. rules-core 按依赖关系确定计算规则的先后：一条规则的表达式或条件引用了另一条规则计算的字段时，被引用的先执行，跨实体也一样（例如明细的 BATCH_QTY 引用 `master.APEX_PL`，主表的汇总引用明细的字段）。明细规则对每一行都执行完，才执行依赖它的主表规则。
2. 没有依赖关系的规则按 `order` 执行，`order` 相同时按规则编码。
3. 全部计算规则执行完后，再执行 `validate`、`ui` 规则和审批条件，它们使用计算后的最终值。
4. 计算规则之间的依赖成环时（包括跨实体成环），保存配置被拒绝，错误中列出环上的规则。
5. 计算过程中不舍入：上游规则的结果按全部精度参与下游计算。保存时才处理小数位，见 write-pipeline 的 WP-15。

## 6. 通用动作

按钮操作的 `actions` 和审批流的 `afterApproval` 使用同一组动作，按数组顺序执行，后一个动作使用前一个动作计算后的结果。

| `action` | 参数 | 作用 |
|---|---|---|
| `applyPendingChanges` | 无 | 把审批的待审修改合并到来源单据 |
| `recalculate` | `target`：`source` 或 `targets` | 按各自的计算规则重算 |
| `updateTargets` | `targets`：每种目标实体一项，含 `entity`、`detailEntity`（可选）、`match`（可选）、`fieldMapping` | 把来源计算后的有效值写到目标 |
| `updateRecords` | `find`（同第 7 节 `targets.find` 的一项）、`fieldMapping` | 按关联键或关联 SQL 找到记录并更新。在按钮操作中，来源是选中单据在数据库中的当前数据（C02 第 1 节），按关联键查找时 `rows` 只能为 `all`；在审批流中的用法见 C08 第 9 节 |
| `escapeHatch` | `operation`：已登记的逃生舱操作 | 调用存储过程，只在用户点名时启用 |

- `fieldMapping` 的每项为 `{"from": "来源实体.字段", "to": "目标字段"}`。`to` 必须在操作或审批流允许写入的范围内，不能是计算字段，也不能是只读的 ERP 列；目标行是 ERP 行而 `to` 是 ERP 列时，整个命令返回 422 FIELD_NOT_WRITABLE。
- 按关联键找到的目标，`from` 取找到它的那一行来源的字段。同一目标被多行来源找到且值不同时，拒绝执行，返回 422 VALIDATION_FAILED。
- `match` 限定目标中要更新的明细行，例如 `{"GOODSID": "COST_GOODS_PRICE.GOODSID"}` 表示只更新物料编号等于来源物料的明细行。

## 7. approvalFlow

### 7.1 字段

| 字段 | 对应你列出的配置项 | 说明 |
|---|---|---|
| `createdSeq` | | 创建先后，第一次保存时分配，之后不变；一张单据命中多个审批流时，批准后动作按它的顺序执行（approval AP-10） |
| `sourceOperation` | 来源操作 | 哪个操作的保存会触发本审批流 |
| `trigger` | 触发条件、保存操作 | `operations`：哪些保存操作触发本审批流，取 `modify`（修改）、`add`（新增）、`delete`（删除），可多选，至少一项，省略时为 `["modify"]`，写出空数组时保存被拒绝，对应命令中各行的 `op`；`changedFields`：必须写，键为来源单据的实体，值为字段数组。对修改，这些字段被修改时才判断；对新增和删除，这里列出的实体有行被新增或删除时就判断，不看字段，所以只监听新增、删除的实体可以写空的字段数组。至少列出一个实体；`operations` 含 `modify` 时，至少一个实体要列出字段，否则保存被拒绝（第 10 节）；没有勾选的操作不触发审批；单据进入审批后整张冻结，本次对这张单据的其他修改也随审批等待（approval AP-01）；`when`：可选的附加条件，写法同第 5 节，可以用 `old.字段` 比较修改前后；`dataItems`：条件需要的数据库数据 |
| `levels` | 审批流程 | 每级的入口：`name`、`when`（为空表示总是满足，写法同第 5 节）、`mode`（`or` 为或签，`and` 为会签）、`approvers`（`{"type": "user", "userId"}`、`{"type": "role", "role"}`，或 `{"type": "sql", "sql": "SELECT USER_ID FROM …", "binds": {…}}`：进入该级时执行，只能是查询语句，返回用户编号） |
| `targets.find` | 关联查询、对象标识 | 查找目标的方式，可以有多项，见 7.2；找到的对象就是锁定对象，保存那一刻起整单锁定（7.3） |
| `targets.selection` | 选择方式 | `all`：找到的目标全部更新；`approverSelects`：审批人从候选中勾选 |
| `display` | 展示内容 | 审批详情"修改内容"的主表和从表，列由管理员自定义，见 7.6 |
| `freeze` | 冻结策略 | 来源单据和候选对象之外还要锁定的单据：按来源的字段用关联键或关联 SQL 关联其他表找到。只决定锁定什么，改不改由批准后动作决定。省略或为空数组时不额外锁定。见 7.3 |
| `afterApproval` | 批准后动作、字段映射 | 第 6 节的通用动作，按顺序执行；全部审批节点都通过后才执行，审批中途任何一级通过都不让修改生效（approval AP-20） |
| `params` | 动作参数 | `[{"name": "effectiveDate", "label": "生效日期", "type": "date", "source": "manual", "required": true, "level": 1}]`。每项必须写 `required`（是否必须有值）。`type` 取 `string`、`number`、`boolean`、`date`；`source` 取 `manual`（审批人在通过时填写，`level` 指在哪一级填写，最终批准时填写的不写 `level`）、`constant`（`value` 为常量）、`expression`（`value` 为表达式）。批准后动作中用 `params.名称` 引用；中途某一级填写的参数也只在最终批准时使用 |
| `propagation` | 传播边界 | 固定为 `end`，可以省略：目标被更新后不再触发审批和同步 |
| `notify` | 通知配置 | `[{"event": "submitted", "to": "levelApprovers"}]`。`event` 取 `submitted`、`levelEntered`、`passed`、`rejected`、`withdrawn`；`to` 取 `levelApprovers`、`applicant`、`{"users": […]}` 或 `{"role": "…"}`。通知文字由平台按固定格式生成，不在这里配置（approval AP-17） |

审批按单据生成：主从页每张单据（一行主表及其明细）、单表页每一行各一个审批。一张单据命中多个审批流时合成一个审批，各审批流的同一级合在一起审批，规则见 [approval](../模块/approval.md) AP-01、AP-04、AP-09、AP-16。

提交审批时，审批流定义随审批实例一起保存。之后再修改审批流配置，已经发起的审批不受影响，仍按提交时的定义走完；批准时的计算和校验按当时的规则执行。

### 7.2 查找目标

- 按关联键：`{"kind": "relationKey", "entity": "COST_GOODS_PRICE", "targetKey": "GOODSID", "sourceKey": "COST_MATERIAL.GOODSID", "rows": "changed"}`。`rows` 为 `changed` 时只用本次有实际变化的来源行，为 `all` 时用全部来源行；来源行怎样选、取哪个时点的值，见 C08 第 9 节。
- 按关联 SQL：`{"kind": "sql", "entity": "COST_PINGGU", "sql": "SELECT …", "binds": {"goodsId": "COST_GOODS_PRICE.GOODSID"}, "recordKeyColumn": "DOC_ID", "rowKeyColumns": [], "labelColumn": "PRODUCT_NAME", "displayColumns": ["DOC_ID", "PRODUCT_NAME", "CURRENT_COST"]}`。
- 关联 SQL 只用来找对象和取展示数据：只能是一条查询语句，参数用绑定变量，结果必须包含 `recordKeyColumn` 和 `rowKeyColumns` 中的每一列（保存时检查，第 10 节）。SQL 本身只读、不加数据库锁、不更新；找到的对象由 approval 登记锁定（7.3）。
- `entity` 是锁定对象所在的实体，锁的是这个实体写入表（第 2 节的 `table`）中的行，`recordKeyColumn` 取这张表的主键值。锁定对象只能是表，不能是视图（第 10 节）。
- 关联 SQL 查出的某一行，`recordKeyColumn` 或 `rowKeyColumns` 中某列的值为空时，表示这条记录在保存前就已经不存在（例如明细还在、所属的单据已被删除）：跳过，不锁定、不更新，也不报错；审批详情中显示为红底的"记录已不存在"（7.6，approval AP-21）。用于 `freeze` 和 `updateRecords` 时同样跳过。
- 查找在保存触发审批时执行一次，结果作为候选对象保存并锁定；批准时不再重新查找。

### 7.3 冻结

保存触发审批的那一刻，在同一个命令事务中锁定（冻结）：

- 来源单据：触发审批的行所在的单据，整单锁定，不用配置；
- 候选对象：`targets.find` 找到的全部对象所在的单据，不论最终是否勾选，不用配置；
- `freeze` 找到的单据：来源单据和候选对象之外还要锁定的单据，省略或为空数组时没有。`freeze` 只决定锁定什么，不决定改什么。`freeze` 每项为以下一种：

| `kind` | 锁定的对象 |
|---|---|
| `relationKey` | 按来源的字段关联其他表找到的单据，格式同 7.2，例如 `{"kind": "relationKey", "entity": "COST_GOODS_PRICE", "targetKey": "GOODSID", "sourceKey": "COST_MATERIAL.GOODSID", "rows": "changed"}` |
| `sql` | 按关联 SQL 找到的单据，格式同 7.2，只需要 `entity`、`sql`、`binds`、`recordKeyColumn`；绑定变量取来源的字段 |

- 锁定以单据为单位：主从页为一行主表及其全部明细，包括审批期间要新增的明细；单表页为一行。找到的是明细行时，锁定它所属的整张单据。没有字段级或明细行级的锁定。
- 锁定对象只能是表，不能是视图：锁定记在实体写入表的主键上（7.2）。
- 查找经 `RelatedQuery` 在提交审批的命令中执行一次，只读，参数用绑定变量；之后不再重新查找。
- 被冻结的单据不能修改、新增明细或删除，直到审批结束；只有来源为本审批的写入可以修改它（approval AP-03）。
- 同一张单据同一时间只属于一个未结束的审批，没有排队。要冻结的单据已被别的审批冻结，或同一命令的两个审批要冻结同一张单据时，整个命令返回 409 FROZEN_BY_APPROVAL（approval AP-06）。
- 冻结记录登记在提交审批的命令事务中，审批结束时解除本审批的全部冻结。
- 锁定范围与更新范围分开：改什么只由批准后动作决定。锁定但最终没被勾选的候选对象，以及没有被批准后动作写到的 `freeze` 单据，审批结束时解锁，内容不变；被写到的照常修改（7.7）。
- 锁定什么完全由配置决定，配置了就锁定，没配置就不锁定。批准后动作中 `updateRecords` 要修改的其他单据，如果需要在审批期间保持不变，配置者应在 `freeze` 中把它们配置为锁定对象（7.7）；没有配置的不锁定，最终批准时由 write-pipeline 加锁并做冻结检查，被别的审批锁定就拒绝（write-pipeline WP-18，approval AP-10）。逃生舱改的单据不经冻结检查（operations OP-04），需要保持不变时同样配置进 `freeze`。
- 审批期间，审批详情中显示的来源单据和候选对象都被本审批锁定，只有本审批能改变它们，不会出现审批中途被别人修改或删除的情况。

成本核算改价（样例一）：

```json
"display": {
  "master": {"columns": [
    {"label": "单据号", "field": "source.DOCID"}, {"label": "产品", "field": "source.GOODSNAME"},
    {"label": "每盒成本", "field": "source.COST_PERBOX"}, {"label": "千片加工费", "field": "source.JGF_PERQP"}
  ]},
  "details": [
    {"title": "原辅料", "rows": "source.COST_MATERIAL", "columns": [
      {"label": "物料", "field": "source.COST_MATERIAL.GOODSID"}, {"label": "物料名称", "field": "source.COST_MATERIAL.GOODSNAME"},
      {"label": "单价", "field": "source.COST_MATERIAL.PRICE"}, {"label": "金额", "field": "source.COST_MATERIAL.AMOUNT"}
    ]},
    {"title": "包材", "rows": "source.COST_PACKAGE", "columns": []}
  ]

```

| 字段 | 说明 |
|---|---|
| `master.columns` | 主表的列，每张审批一行 |
| `details[]` | 从表，每张一个 Tab，按顺序显示；`columns` 为空的从表不显示 |
| `details[].rows` | 从表每行是什么：`source.<明细实体>`：来源单据中有修改、新增或删除的明细行；`target`：每张候选单据一行；`target.<明细实体>`：每张候选单据中会被批准后动作改变的明细行 |
| `details[].rowsFilter` | `changed`（默认）：只列有变化的行；`all`：`source.<明细实体>` 时列出全部明细行 |
| `columns[].label` | 列标题 |
| `columns[].field` | 取哪个字段：`source.字段`（来源主表）、`source.<明细实体>.字段`、`target.字段`（候选单据的主表）、`target.<明细实体>.字段`。一行可以同时取明细和它所属主表的字段，例如上例从表一行里既有成本单的明细，也有这张成本单的每盒成本 |

取值和显示：

- 来源单据的修改后值按全部待审修改一起计算；候选单据的修改后值按"只把这次修改应用到这张单据"计算。两者都包括计算带出的字段，由 rules-core 实时算出。
- 新增的行标为"新增"，只显示新值；删除的行标为"删除"，显示删除前的值。
- "修改内容"只显示触发审批的来源单据和锁定的候选对象，它们从保存那一刻起都被本审批锁定（7.3）。
- 保存时关联 SQL 查出的某一行主键为空（这条记录在保存前就已经不存在），在该审批流的候选单据从表最后显示一行"记录已不存在"，整行红底，带上能取到的单据号和 `labelColumn` 的值，不能勾选，批准时跳过（approval AP-21）。
- 从表的行是候选单据或其明细时，审批人按单据勾选（`selection` 为 `approverSelects`）：同一张单据的几行连在一起，取自 `target.字段` 的列合并显示，勾选框在这组行的最前面，勾选一次就是勾选这张单据。`selection` 为 `all` 的审批流不显示候选单据。
- 字段的小数位取页面视图；`field` 必须属于对应的实体，`rows` 为 `source.X` 的从表不能取 `target` 的字段，反之亦然。
- 没有配置 `display` 时，主表显示来源单据中有变化的字段，从表按明细实体各一张，显示有变化的行和字段。

一张单据同时命中多个审批流时（approval AP-01、AP-09），合成一个审批，详情这样显示：

- 审批进度：各审批流的入口按级别排在一起，"来自审批流"列标出每个入口属于哪个审批流。
- 修改内容中，来源单据的主表和 `source.<明细>` 从表只显示一份：列取这些审批流 `display` 的并集，按 `createdSeq` 顺序排列，同一字段只出现一次。每行末尾加一列"触发审批"，列出这一行触发的审批流，例如同一行既改了价格又换了物料，就列出两个；没有触发审批、随整单等待的行，显示"随审批等待"。
- `target` 和 `target.<明细>` 从表按审批流分开，各显示为一个 Tab，标题后注明审批流名称；只有 `selection` 为 `approverSelects` 的审批流才有。

### 7.7 样例三：成本核算 → 物料清单 → 其他含同一物料的成本单

成本单改了某个物料的单价，审批通过后先同步到物料清单，再同步到其他含这个物料的成本单。要同步的其他成本单由配置者在 `freeze` 中用关联 SQL 锁定，批准后动作按顺序修改（业务例子 E36）。

```json
{
  "type": "approvalFlow",
  "key": "COST_TO_GOODS_AND_COSTS",
  "name": "成本核算改价 → 物料清单 → 其他成本单",
  "content": {
    "createdSeq": 3,
    "sourceOperation": "COST_PINGGU.save",
    "trigger": {"operations": ["modify"], "changedFields": {"COST_MATERIAL": ["PRICE"]}, "when": null, "dataItems": []},
    "levels": [
      {"level": 1, "entries": [{"name": "价格审核", "when": null, "mode": "or", "approvers": [{"type": "user", "userId": "111"}]}]}
    ],
    "targets": {
      "find": [{"kind": "relationKey", "entity": "COST_GOODS_PRICE", "targetKey": "GOODSID", "sourceKey": "COST_MATERIAL.GOODSID", "rows": "changed"}],
      "selection": "all"
    },
    "display": {"master": {"columns": [{"label": "单据号", "field": "source.DOCID"}, {"label": "产品", "field": "source.GOODSNAME"}]},
      "details": [{"title": "原辅料", "rows": "source.COST_MATERIAL", "columns": [{"label": "物料", "field": "source.COST_MATERIAL.GOODSID"}, {"label": "单价", "field": "source.COST_MATERIAL.PRICE"}]}]},
    "freeze": [
      {"kind": "sql", "entity": "COST_PINGGU", "sql": "SELECT DISTINCT D.DOCID AS DOC_ID FROM T_COST_PINGGU_DTL D WHERE D.GOODSID = :goodsId", "binds": {"goodsId": "COST_MATERIAL.GOODSID"}, "recordKeyColumn": "DOC_ID"}
    ],
    "afterApproval": [
      {"action": "applyPendingChanges"},
      {"action": "recalculate", "target": "source"},
      {"action": "updateTargets", "targets": [{"entity": "COST_GOODS_PRICE", "fieldMapping": [{"from": "COST_MATERIAL.PRICE", "to": "ZX_PRICE"}]}]},
      {"action": "recalculate", "target": "targets"},
      {"action": "updateRecords", "find": {"kind": "relationKey", "entity": "COST_MATERIAL", "targetKey": "GOODSID", "sourceKey": "COST_MATERIAL.GOODSID", "rows": "changed"}, "fieldMapping": [{"from": "COST_MATERIAL.PRICE", "to": "PRICE"}]}
    ],
    "propagation": "end",
    "notify": [{"event": "submitted", "to": "levelApprovers"}, {"event": "passed", "to": "applicant"}, {"event": "rejected", "to": "applicant"}]
  }
}
```

- `freeze` 的关联 SQL 找出含这个物料的全部成本单（包括来源单据自己），保存时整单锁定。
- 最后一步 `updateRecords` 按关联键找原辅料明细（`entity` 为明细实体 COST_MATERIAL）：物料编号等于来源中改了价的那一行的明细，单价取那一行的新值（第 6 节"按关联键找到的目标，`from` 取找到它的那一行来源的字段"）。来源单据自己的那一行已经是新值，不算变化。写入时按各成本单自己的计算规则带出金额等字段；`propagation` 为 `end`，这些修改不再触发审批。
- 详情只显示来源单据（7.6）；`selection` 为 `all`，物料清单和其他成本单都不显示。

## 8. role

```json
{
  "name": "成本会计",
  "admin": false,
  "pages": {
    "COST_PINGGU": {
      "buttons": ["system:save", "system:addRow", "system:deleteRow", "system:advancedSearch", "master:copyRow", "master:syncPrice", "COST_MATERIAL:copyRow", "export:cost-pinggu-export"],
      "rows": {"mode": "visual", "logic": "AND", "conditions": [{"field": "CREATE_BY", "fieldLabel": "创建人", "op": "eq", "valueType": "dynamic", "value": "${username}"}], "sql": "CREATE_BY = ${username}"},
      "columns": {"master": {"PRICE": {"visible": true, "editable": false}}, "COST_MATERIAL": {}}
    }
  }
}
```

- `rows` 是行权限，格式与旧系统相同，有两种写法：
  - 可视化：`mode` 为 `visual`；`logic` 为 `AND` 或 `OR`；`conditions` 每项含 `field`、`fieldLabel`、`op`、`valueType`（`static` 或 `dynamic`）、`value`；`sql` 是按条件生成的 SQL 条件。`op` 取 `eq`、`ne`、`gt`、`ge`、`lt`、`le`、`like`、`in`、`isNull`、`isNotNull`。
  - 自定义 SQL：`rows` 直接是一个 SQL 条件字符串，例如 `"CREATE_BY = ${username}"`。
- 两种写法都可以用占位符 `${userId}`、`${username}`。平台把占位符换成绑定变量执行，不拼接字符串。
- 保存时校验：SQL 条件只能是一个条件表达式，不能含分号和数据修改语句。
- 没有 `rows` 时，可以访问页面主表的全部行；明细随主表。
- `buttons` 是按钮权限，与旧系统的 BUTTON_POLICY 相同，区别是分组改用区域编码，界面上仍显示区域标题：
  - `system:<动作>`：页面级按钮，取 `save`、`addRow`、`deleteRow`、`advancedSearch`；
  - `master:<动作>`、`<明细实体>:<动作>`：区域中的按钮，例如 `master:copyRow`、`master:syncPrice`；
  - `export:<导出编码>`：可以使用的导出配置；
  - `["*"]` 表示该页面的全部按钮和导出。
- 后端按 `buttons` 检查：保存需要 `system:save`；Patch 有新增行需要 `system:addRow`，或者该区域的 `copyRow`（复制出的行在后端也是新增行）；Patch 有删除需要 `system:deleteRow`；按钮操作需要该按钮的键；按导出配置导出需要 `export:<编码>`；默认导出当前页面不需要单独授权。审批的处理由审批流决定，不使用按钮权限；审批进度所有人都能查看。
- `columns` 是列权限，格式同旧系统的 COLUMN_POLICY，按区域列出字段的 `visible`、`editable`、`required`，只能收紧可见、可编辑，或增加必填。
- `admin` 必须写，为 true 的角色可以使用配置和管理功能。

```json
{"page": "COST_PINGGU", "name": "物料成本核算表导出", "fileName": "物料成本核算表", "font": "Calibri",
 "master": {"sheet": "物料成本核算", "sql": "SELECT m.DOCID AS DOCID, m.DOCID AS \"Summary ID\", m.GOODSNAME AS \"Product Name\" FROM T_COST_PINGGU m", "keyColumn": "DOCID", "columns": [{"field": "Summary ID", "header": "Summary ID"}, {"field": "Product Name", "header": "Product Name"}]},
 "details": [{"sheet": "原辅料明细", "sql": "SELECT d.DOCID AS DOCID, d.DTLID AS \"Details ID\" FROM T_COST_PINGGU_DTL d", "linkColumn": "DOCID", "columns": [{"field": "Details ID", "header": "Details ID"}]}]}
```

以上依次为 `menu`、`dict`、`lookup`、`export` 的 `content`。

- dict 的 `items[].order` 是显示顺序，必须写。
- lookup 的 `keywordColumns` 是按关键字搜索的列，必须写；不按关键字搜索时写空数组，这时 Lookup 对话框不显示搜索框，带关键字的查询被拒绝（C09 第 4 节，queries-export 的 QE-09）。

`export` 是按自定义查询导出的配置，对应旧系统的导出配置（例如成本核算的 cost-pinggu-export）。`sql` 只能是一条查询语句；`keyColumn` 是主表结果中与页面主表主键相等的列，可以重复；`linkColumn` 是明细结果中与 `keyColumn` 关联的列。导出时平台用页面主表的行权限和当前查询条件限定结果（C09 第 4 节的 `scope`），不在 SQL 里拼接条件；列按 `columns` 的顺序导出。
导出文件的版式与旧系统相同：

- 主表一张工作表，名称取 `master.sheet`。
- `detailLayout` 为 `perMaster`（默认）时，每张主单一张明细工作表，名称为"明细_<主单主键>"，重名时加序号；表内每个明细配置一个块，依次为块标题行（取该明细的 `sheet`）、表头行和数据行。为 `perDetail` 时，每个明细配置一张工作表。
- 主表中 `keyColumn` 所在的单元格链接到这张主单的明细工作表；明细工作表中 `linkColumn` 所在的单元格链接回主表对应的行。
- `columns[].header` 中用 `/` 分隔表示多级表头，例如 `"成本/单价"`。
- 字体取 `font`，默认 Calibri；列宽按每列最长的内容自动调整；表头加粗并带底色。
- 数值写成文本单元格（queries-export 的 QE-06）。


## 10. 保存时的校验

config 保存任何配置项时都执行以下校验，不通过时拒绝保存（422 VALIDATION_FAILED），当前版本不变：

- 引用的实体、字段、操作、页面、审批流、Lookup、字典都存在。
- 表和列在数据库中存在（经 db-core 的 `SchemaInspector`）。
- 没有 `erpRow` 的实体，其 ERP 列在任何层都不能设为可写，也不能出现在 `writableFields` 和 `fieldMapping.to` 中；任何实体的 ERP 列都不能出现在逃生舱的 `writes` 中；`erpRow.column` 不能设为可写。
- 下层只能收紧可见、可编辑，必填只能增加。
- `formLayout` 不越出 24 列，不引用不存在的字段。
- 表达式和条件能被 rules-core 解析，计算规则的依赖不成环，规则包能编译通过。
- 关联 SQL、数据项 SQL 和导出 SQL 只能是一条查询语句，参数用绑定变量；关联 SQL 的结果包含 `recordKeyColumn` 和 `rowKeyColumns` 中的每一列，导出 SQL 的结果包含 `keyColumn` 或 `linkColumn`。例如 `rowKeyColumns` 填了 `DTL_ID` 而 SQL 没有选出这一列时，拒绝保存，提示缺少的列。
- 审批流 `targets.find` 和 `freeze` 中每一项的 `entity` 必须是已有实体，`freezable` 为 true，写入表 `table` 在数据库中必须是表，不能是视图（经 `SchemaInspector` 的 `object_type`）；来源单据的实体 `freezable` 也必须为 true；`sourceKey` 和绑定变量必须引用来源实体中存在的字段。
- 审批流的级别从 1 开始连续，每个入口至少有一个审批人；`trigger.operations` 至少选一项，只能取 `modify`、`add`、`delete`。
- 审批流的 `trigger.changedFields` 至少列出一个实体。每个键必须是来源单据的实体，即以 `sourceOperation` 为保存操作的页面的主表实体或其明细实体；列出的字段必须属于该实体。`trigger.operations` 含 `modify` 时，至少一个实体列出了字段；只监听新增、删除时，实体的字段数组可以为空。
- 页面区域按钮的 `action` 为业务动作时，必须写 `operation` 和 `requiresSelection`；为内置动作时，这两项都不能写。
- `kind` 为 `action` 的操作中，`updateRecords` 按关联键查找时 `rows` 只能为 `all`：按钮命令不带修改（C02 第 1 节），没有"本次有变化的行"。
- `approvalRequired` 的每条规则，至少有一个审批流的来源操作是 `sourcePages` 中某个页面的保存操作。
- 实体的序列 `<表名>_SEQ` 必须已在数据库中存在；平台不创建序列。
- 审批人 SQL、`compare.source` 只能是查询语句或表、视图名，参数用绑定变量；`manual` 参数的 `level` 必须是该审批流已有的级别。
- 仍被其他配置引用的配置项不能删除。
