
| `type` | `content` 见 | 说明 |
|---|---|---|
| `entity` | 第 2 节 | 实体与表、字段的对应 |

### 1.1 字段的省略

`content` 中的字段按以下规则读取，config 保存和 migration 导入相同；字段的值照常按 C01 的格式。

- 下表没有列出的字段都必须写出；值可以为 null 的字段，没有值时写 null。
- 决定行为的字段必须明确写出，平台不补默认值：page 的 `audit`、`detailMode`，operation 的 `propagation`，rule 的 `order`，approvalFlow 的 `order`、`operations`、`params[].required`，role 的 `admin`，dict 的 `items[].order`，lookup 的 `keywordColumns`。配置界面可以预填这些字段，但保存时必须带上。
- 下表中省略时为"空"的是数组或对象，省略等于写出空数组或空对象。
- 省略时为"无"的是可选的单个值，省略表示没有设置这一项，含义见各字段的说明。对象类型的可选字段也是这样，例如 page 字段的 `lookup.filter` 省略表示不筛选，不等于空对象 `{}`。
- 省略时为具体值的，是字段自己的默认值，优先于上面两条。例如 approvalFlow 的 `enabled` 省略时为 `true`，page 字段 `lookup` 的 `multiple` 省略时为 `false`。

## 2. entity

```json
{
  "table": "T_COST_PINGGU",
  "primaryKey": "DOCID",
  "freezable": true,
  "fields": [
    {"name": "DOCID", "column": "DOCID", "label": "单据号", "type": "number", "scale": 0, "source": "own", "role": "system"},
    {"name": "GOODSNAME", "column": "GOODSNAME", "label": "产品名称", "type": "text", "source": "erp", "role": "input"},
    {"name": "TOTAL_COST", "column": "TOTAL_COST", "label": "总成本", "type": "number", "scale": 2, "grouping": true, "source": "own", "role": "calculated"}
  ],
  "details": [{"entity": "COST_MATERIAL", "parentKey": "DOCID"}],
  "fieldDefaults": {"TOTAL_COST": {"visible": true, "editable": false, "required": false}}
}
```

- `source`：`erp` 为 ERP 列，由 ERP 同步写入；`own` 为平台自有列。
- `erpRow`：可选，标识哪些行来自 ERP，例如物料表 `{"column": "ISERP", "value": "1", "localValue": "0"}`。
  - 没有 `erpRow` 的实体，ERP 列在所有行上都只读，任何操作都不能写。
  - 有 `erpRow` 的实体，ERP 列只在 ERP 行（该列等于 `value`）上只读；本地行和新增行（含复制出的行）的 ERP 列由平台维护，按页面和角色设置判断能否编辑。
  - `column` 本身只由平台写：新增和复制的行由平台设为 `localValue`，不从源行复制，用户不能修改。
- `role`：`input`、`calculated`（由规则计算，用户不能输入）、`system`（主键等）。
- `freezable`：是否可被审批冻结；为 false 的实体，写入时不做冻结检查，也不能作为审批流所属页面的表格，它的表不能作为冻结表（第 10 节）。
- `approvalRequired`：可选，必须审批的字段规则，对应旧系统的 `APPROVAL_REQUIRED`。例如物料表 `[{"fields": ["ZX_PRICE"], "when": {"logic": "AND", "conditions": [{"field": "ISERP", "op": "eq", "value": "1"}]}, "sourcePages": ["GOODS_PRICE_MANAGE"]}]`。
  - `when` 只用本行字段，`op` 取 `eq`、`ne`、`isNull`、`isNotNull`，不能用 SQL；修改前或修改后的行满足 `when` 都算命中；省略 `when` 时所有行都满足。
  - 命中条件：修改了 `fields` 中的字段，或者删除了满足 `when` 的行，或者新增了满足 `when` 且填写了 `fields` 的行。
  - 规则属于实体，与页面和审批流无关：任何写入口写这个实体都检查，停用或删除审批流不会让规则失效。处理见 approval 的 AP-18。
- `fields[].column` 为 null 时，字段只存在于 `readView` 中，只读显示，不写入。从视图导入列时，表中没有的列按这种方式生成。
- `fields[].default`：新增行的默认值，与旧系统相同，有三种写法：
  - `{"type": "static", "value": "1"}`：固定值；
  - `{"type": "builtin", "value": "currentUserId"}`：取值 `currentUserId`、`currentUserName`、`currentDeptId`、`currentDeptName`、`currentRoleCode`、`currentTime`（日期字段取当天，日期时间字段取当前时间）；
  - `{"type": "options", "value": ["A", "B"]}`：单元格用下拉选择这些值，新增行默认取第一个。
  - 没有配置时，数值字段默认为 0，其他字段为空，与旧系统相同。赋值时机见 write-pipeline 的 WP-16。
- `fields[].scale`：数值的显示小数位，只用于显示。`fields[].grouping`：为 true 时数值显示千分位，整数部分每三位加一个英文逗号，例如批量 3500000 显示为 3,500,000、每批物料成本 1234567.891（`scale` 为 2）显示为 1,234,567.89；省略时为 false。两项都只用于表格、表单和汇总行的显示，编辑框中、计算、保存和导出（数值单元格）都用原来的值；只对数值字段起作用。对应旧系统列配置 `rulesConfig.precision`、`useGrouping`（配置页"精度""千分位"）。
- `fields[].compare`：可选，与历史或关联数据对比，对应旧系统的 `rulesConfig.compare`：
  - `{"mode": "field", "field": "LAST_PRICE", "format": "both"}`：与同一行的另一个字段对比；
  - `{"mode": "query", "source": "T_COST_GOODS_HIS_V", "keys": [{"current": "GOODSID", "compare": "GOODSID"}], "field": "PRICE", "format": "percent"}`：按关联键到另一个表或视图取对比值；
  - `format` 取 `value`（差值）、`percent`（百分比）、`both`。结果只用于显示，见 queries-export 的 QE-10。
- 新增行的主键取序列 `<表名>_SEQ` 的下一个值，例如 `T_COST_PINGGU` 用 `T_COST_PINGGU_SEQ`。
- `readView`：可选的视图名。设置后，列表、单据加载、审批详情，以及写入管道加锁读取当前值，都经这个视图读取；写入仍写到 `table` 的同名列。视图只能基于这一张表，必须包含主键和实体的全部字段。例如物料清单用 `T_COST_GOODS_PRICE_V`：视图过滤掉了"产成品""半成品"，视图中的 `ZX_PRICE` 在表中的 ZX_PRICE 为空时取 PRICE。
- `updatedByColumn`：可选，写入修改人的列，是 `table` 中的列名，不是实体字段，也不能是实体字段写入的列。设置后，任何写入口新增、修改这个实体的行时，写入管道在同一条语句里把这一列写成当前用户的登录名（C04 的 `username`）；审批通过时写入的行写执行通过的审批人（write-pipeline 的 WP-20）。删除不写。例如物料清单 `"updatedByColumn": "UPDATE_BY"`：视图 `T_COST_GOODS_PRICE_V` 按 UPDATE_BY 判断 ERP 行是否被人工改过（不是 `ERP_SYNC` 时 ROW_CLASS_FLAG 为 `erp-updated`，黄底），ERP 同步过程只在 UPDATE_BY 为空或为 `ERP_SYNC` 时覆盖参考价格。来源：旧系统每次保存写 UPDATE_BY = 当前用户名（`cost-server/.../dynamic/service/DynamicDataService.java` 第 290–293、392–393 行，用户名取 `SecurityUtils.getCurrentUsername()`，即登录用的用户名）；审批通过在审批人的请求中执行同一段保存（`ConfiguredApprovalRuntime.java` 的 `applyPending`）；用户 2026-10-30 同意按旧系统做。字段名由实施者决定。

```json
    "buttons": [{"action": "addRow", "label": "新增"}, {"action": "copyRow", "label": "复制"}, {"action": "deleteRow", "label": "删除"}, {"action": "syncPrice", "label": "同步价格", "operation": "COST_PINGGU.syncPrice", "requiresSelection": true}, {"action": "saveGridConfig", "label": "保存列配置"}], "grid": {"sideBar": true, "cellSelection": true, "groupBy": []},
    "formLayout": [{"field": "GOODSNAME", "x": 0, "y": 0, "w": 12, "h": 1}]
  },
  "details": [
    {"entity": "COST_MATERIAL", "title": "材料", "fields": {}, "buttons": [{"action": "addRow", "label": "新增"}, {"action": "copyRow", "label": "复制"}, {"action": "deleteRow", "label": "删除"}], "grid": {"sideBar": true, "cellSelection": true, "groupBy": []}, "formLayout": []}
  ]

```

- `layout` 为 `single` 时是单表页，`details` 为空。
- `audit`：本页面的命令是否记录审计差异（write-pipeline 的 WP-11）；`detailMode`：明细的默认显示方式，`tabs` 或 `stack`。两项都必须写，单表页也要写 `detailMode`（第 1.1 节）。
- `fields` 中只写本页面要改的设置：`visible`、`editable` 只能收紧，`required` 只能加；另可设 `width`、`pinned`、`dictType`、`dictFreeText`、`lookup`、`aggregate`、`searchable`。
- `dictType`：单元格从这个字典的下拉中选，保存字典项的 `value`，显示 `label`。`dictFreeText` 为 true 时下拉中还可以直接填写字典以外的值，保存填写的文本（显示也是这个文本）；仍然只存一个值；省略时为 false，只能选字典中的值。对应旧系统的"下拉（可填写）"编辑器（`tagSelectCellEditor`）。例如成本核算主表"分类"（PINGGU_CLASS）：字典项为委托研发、委托转移、自主立项、平台业务（`value` 与 `label` 相同），同旧系统列配置的选项值，库中存选中或填写的文本。
- `searchable`：查询，对应旧系统列配置的"查询"。为 true 时，高级查询对话框一打开就列出这个字段的条件（预置条件），用户填值、勾选即可查询；省略表示不预置，用户仍可以用"添加条件"按这个字段查询。只对可见字段起作用，任何类型的字段都可以设。例如成本核算主表、原辅料、包材的可见字段，物料清单除单价（ZX_PRICE）以外的可见字段，同旧系统 cost-pinggu、goods-price-manage 的列配置。预置条件的排列、默认运算符和用 Lookup 选值见 frontend-page 的 FP-22。
- `aggregate`：汇总行，对应旧系统列配置的"求和"（`rulesConfig.aggFunc` 为 `sum`）。取 `sum` 时，这一列在表格底部固定的汇总行中求和；只能用于数值字段；省略表示这一列不汇总。区域中有求和的列时才显示汇总行，汇总行不能编辑、不能选中，没有求和的列为空：
  - 主表区：对全部满足当前查询条件（行权限、筛选、高级查询）的行求和，不只是当前页（queries-export 的 QE-04），再加上还没保存的修改；
  - 明细区：对当前单据这个明细的全部行求和；
  - 新增的行计入，标为删除的行不计入（与 C07 的汇总相同）；空值按 0 计入；显示的小数位和千分位同这一列（C05 `scale`、`grouping`）。
  - 例如成本核算主表的每批物料成本（TOTAL_COST）、原辅料和包材的金额（COST_BATCH）求和，同旧系统 cost-pinggu。
- `lookup` 的写法：`{"code": "GOODS", "fill": {"GOODSID": "GOODSID", "GOODSNAME": "NAME"}, "multiple": false, "filter": {"column": "GOODSTYPE", "from": "row", "field": "PACKTYPE"}, "fillBack": true}`，对应旧系统的 Lookup 规则：
  - `multiple` 为 true 时可以选多行，同一个回填字段的值用英文逗号连接；省略时为 false；
  - `filter` 只查 `column` 等于某个值的行，值取当前行的 `field`（`from` 为 `row`），或者取点开的单元格的值（`from` 为 `cell`，不用 `field`）；值为空时不过滤；省略 `filter` 表示不筛选；
  - `fillBack` 为 false 时只查看、不回填，只读的单元格也可以打开；省略时为 true。
  - 这三项省略时的值与 C05 页面视图相同。
- `formLayout` 由管理员拖动编辑，所有人共用。
- `buttons`：本区域工具栏和右键菜单中的按钮，格式同旧系统的组件按钮。`action` 为内置动作 `addRow`（新增）、`copyRow`（复制）、`deleteRow`（删除）、`saveGridConfig`（保存列配置），或业务动作；业务动作用 `operation` 引用操作库中的操作，并且必须写 `requiresSelection`：为 true 时没有选中行就不可用，后端也检查（operations 的 OP-05）。`requiresSelection` 只规定执行的前提，实际处理的行和权限仍由后端检查（OP-05）。内置动作不写 `operation` 和 `requiresSelection`，是否需要选中行由平台统一规定，见 config 的 CF-03。保存、高级查询是页面级按钮，不用写在区域里。
- 按钮显示出来还要角色有权限，见第 8 节。新增、删除也按区域授权（`<区域>:addRow`、`<区域>:deleteRow`），只在页面配置放了它们的区域显示。
- `modify` 用作区域的修改权限键（`<区域>:modify`，第 8 节），不是按钮，业务动作不用这个名字。

```json
{
  "label": "保存",
  "kind": "save",
  "writableFields": {"COST_PINGGU": ["QTY", "REMARK"], "COST_MATERIAL": ["GOODSID", "USAGE", "PRICE"]},
  "impact": ["COST_PINGGU", "COST_MATERIAL"],
  "actions": [],
  "rowNotFound": "skip",
  "propagation": "continue"
}
```

| 字段 | 说明 |
|---|---|
| `kind` | `save`：页面保存，修改来自 Patch；`action`：按钮，按 `actions` 执行；`escapeHatch`：逃生舱，只在用户点名时启用 |
| `writableFields` | 本操作允许写入的字段。审批流通过后的操作（7.5）不受这一项约束，也不按个人权限，只是不能写计算字段和 ERP 列 |
| `impact` | 本操作可能修改的实体，用于返回受影响行 |
| `actions` | `kind` 为 `action` 时的通用动作，见第 6 节 |
| `rowNotFound` | 要修改或删除的行已被删除时（按钮操作为选中的行，C02 第 1 节）：`skip`（默认，跳过并提示）或 `reject` |
| `propagation` | `continue` 或 `end`，必须写；为 `end` 时，本操作写到的目标不再触发审批和同步 |
| `procedure`、`writes` | 只用于 `escapeHatch`：登记调用的存储过程和会修改的表、列，不能包含 ERP 列 |

## 5. rule

规则和旧系统一样按表单编辑，保存在配置中，不需要图形编辑器。config 保存时把每条规则转成 JDM（只用输入、表达式、输出节点），编进规则包（[C07](C07-规则内核接口.md)）；用户不直接编辑 JDM。

计算规则（包材明细的批量，按物料名称分两种算法）：

```json
{"layer": "entity", "target": "COST_PACKAGE", "category": "calc", "field": "BATCH_QTY", "order": 10, "dataItems": [],
 "branches": [
  {"when": "matches(GOODSNAME, '桶|说明书|小盒|标签|瓶|盖|干燥剂|序列化')", "expression": "master.APEX_PL / master.P_PERPACK * (1 + EXADD_MATER / 100)"},
  {"when": "matches(GOODSNAME, '硬片|铝箔|复合膜')", "expression": "PER_HL * master.APEX_PL * (1 + EXADD_MATER / 100) / 1000000"}]}
```

界面规则（ERP 来的物料整行不能编辑，条件用可视化写法）：

```json
{"layer": "page", "target": "GOODS_MANAGE", "category": "ui", "field": null, "order": 10,
 "when": {"logic": "AND", "conditions": [{"source": "row", "field": "ISERP", "op": "eq", "value": "1"}]},
 "effect": {"editable": false}}
```

| 字段 | 说明 |
|---|---|
| `layer` | `entity`：写到该实体时都执行；`operation`：执行该操作时执行；`page`：只管界面，只在前端执行（预览和显示求值） |
| `target` | 实体编码、操作编码或页面编码 |
| `category` | `calc`：计算字段的值；`validate`：校验；`ui`：可编辑、必填和样式 |
| `field` | 规则作用的字段，属于规则所在的实体（主表或某个明细）。`calc` 必填；`ui` 为空时作用于整行 |
| `when` | 条件：表达式文本，或可视化条件（`logic` 为 `AND` 或 `OR`；`conditions` 每项含 `source`（`row` 本行、`master` 主表）、`field`、`op`、`value`，`op` 的取值同第 8 节）。为空表示总是成立 |
| `expression`、`branches` | `calc` 的计算表达式；分情况计算时用 `branches`，按顺序取第一个 `when` 成立的分支，都不成立时字段值不变 |
| `level`、`message` | `validate`：`when` 成立时给出 `reject`（拒绝保存）或 `prompt`（提示）和提示文字。只检查有修改的行（不含删除的行），主表行也一样：本次新增、修改的行，加上计算带出变化的行（计算字段算出的值与修改前不同，例如改了主表批量后每批数量变了的原辅料行、明细单价改了后汇总变了的主表行）；没有修改的行即使不满足条件也不拒绝、不提示（同旧系统保存时只校验有修改的行，计算带出的变化也算修改，C07 v7） |
| `effect` | `ui`：`when` 成立时生效，可含 `editable`、`required`、`rowStyle`、`cellStyle`。页面一显示就按行的值生效，不需要先编辑（同旧系统 GRID_STYLE 渲染行时算样式，C07 v6 第 3.1 节）；单据有修改后按修改后的值 |
| `order` | 整数，必须写；只在两条规则之间没有依赖关系时决定先后，执行顺序见下面的规定 |
| `dataItems` | 规则需要的数据库数据：`[{"name": "usage", "sql": "SELECT … WHERE GOODSID = :goodsId", "binds": {"goodsId": "GOODSID"}}]`，表达式中写作 `data.usage`。有数据项的规则只在后端执行 |

表达式使用 ZEN 表达式语法，数值按十进制计算，不经过浮点。取值约定：

- 作用字段属于主表时，表达式对每张单据求值一次：主表字段直接写字段名；明细写明细实体编码，值是行的数组，例如 `sum(map(COST_MATERIAL, #.USAGE * #.PRICE))`。
- 作用字段属于明细时，表达式对该明细的每一行求值一次：本行字段直接写字段名，主表字段写 `master.字段`。
- `old.字段` 是本命令开始前的正式值：后端取加锁读取时读到的当前值，前端取从后端加载到的值，都不另查数据库；新增行为空；本次没有修改的字段，`old` 与当前值相同。`context.userId`、`context.role`、`context.today` 取执行上下文。
- 审批流的入口条件是 SQL 片段（第 7 节），由 approval 在计算之后执行，不经过 rules-core。

执行顺序：

1. rules-core 按依赖关系确定计算规则的先后：一条规则的表达式或条件引用了另一条规则计算的字段时，被引用的先执行，跨实体也一样（例如明细的 BATCH_QTY 引用 `master.APEX_PL`，主表的汇总引用明细的字段）。明细规则对每一行都执行完，才执行依赖它的主表规则。
2. 没有依赖关系的规则按 `order` 执行，`order` 相同时按规则编码。
3. 全部计算规则执行完后，再执行 `validate`、`ui` 规则，它们使用计算后的最终值；审批流入口条件中的 `:new_` 也取计算后的最终值。`validate` 只对本次新增、修改的行执行，`ui` 对全部行执行。
4. 计算规则之间的依赖成环时（包括跨实体成环），保存配置被拒绝，错误中列出环上的规则。
5. 计算过程中不舍入：上游规则的结果按全部精度参与下游计算。保存时才处理小数位，见 write-pipeline 的 WP-15。

## 6. 通用动作

按钮操作的 `actions` 使用这组动作，按数组顺序执行，后一个动作使用前一个动作计算后的结果。审批流通过后的操作写在展示数据的每一块里（7.5），写法与本节不同：按修改表的主键写入，取值是 SQL 表达式。

| `action` | 参数 | 作用 |
|---|---|---|
| `recalculate` | `target`：`source` 或 `targets` | 按各自的计算规则重算 |
| `updateTargets` | `targets`：每种目标实体一项，含 `entity`、`detailEntity`（可选）、`match`（可选）、`fieldMapping` | 把来源计算后的有效值写到目标 |
| `updateRecords` | `find`（查找方式见 6.1）、`fieldMapping` | 按关联键或关联 SQL 找到记录并更新。来源是选中单据在数据库中的当前数据（C02 第 1 节），按关联键查找时 `rows` 只能为 `all` |
| `replaceDetails` | `entity`：明细实体；`sql`；`binds`（写法同 6.1，只引用主表字段） | 替换每张选中单据的这个明细：删掉它的全部行，再把 SQL 查出的每一行新增为一行。每张选中单据执行一次 SQL |
| `updateRows` | `entity`、`sql`、`recordKeyColumn`、`rowKeyColumns`（后两项同 6.1） | 不看选中行：SQL 执行一次，每一行是一条要改的记录和它的新值，涉及哪些单据由 SQL 的结果决定 |
| `escapeHatch` | `operation`：已登记的逃生舱操作 | 调用存储过程，只在用户点名时启用 |

- `fieldMapping` 的每项为 `{"from": "来源实体.字段", "to": "目标字段"}`。`to` 必须在操作允许写入的范围内，不能是计算字段，也不能是只读的 ERP 列；目标行是 ERP 行而 `to` 是 ERP 列时，整个命令返回 422 FIELD_NOT_WRITABLE。
- 按关联键，或按绑定明细字段的关联 SQL（6.1）找到的目标，`from` 取找到它的那一行来源的字段，`match` 中引用来源的字段也取这一行的值；`from` 和 `match` 引用主表字段时都取主表的值（主表和明细有同名字段时也一样，例如成本单主表的 GOODSID 是产品、原辅料的 GOODSID 是物料）。冲突按实际要写的目标行判断：带 `detailEntity` 时目标行是 `match` 选出的明细行，否则是找到的目标本身；同一目标行被写入不同的值时，拒绝执行，返回 422 VALIDATION_FAILED。例如成本单 D 中物料 115 的单价为 80、116 为 12：按物料编号找其他成本单的原辅料明细并写单价，由 116 那一行找到的明细写 12，由 115 那一行找到的写 80；成本单 E 同时含 115 和 116、作为整张单据被这两行都找到，`match` 按物料编号选明细时，E 中 115 那一行写 80、116 那一行写 12，不冲突；D 有两行 115、单价分别为 80 和 82 时，E 中 115 那一行被写入两个值，返回 422。
- `match` 限定目标中要更新的明细行，例如 `{"GOODSID": "COST_GOODS_PRICE.GOODSID"}` 表示只更新物料编号等于来源物料的明细行。
- `replaceDetails`、`updateRows` 的 SQL 只能是一条查询语句，在命令事务中只读执行。结果中除主键列外，每一列的列名就是要写的字段名，值就是这一列的值；这些字段必须在 `writableFields` 中，不能是计算字段、只在视图中的字段（`column` 为 null）或只读的 ERP 列。计算字段由计算规则算出；名称、分类这类只在视图中的字段，按页面上这个字段的 Lookup 回填带出（write-pipeline 的 WP-08）；`replaceDetails` 新增的行没有写的字段不补默认值（WP-16 的例外），不写进表，取数据库的列默认值（没有默认值为空），与旧 P_COST_BOM_INSERT 相同；关联字段取所属单据的主键。
- `replaceDetails` 的 `binds` 取选中单据主表计算后的值；新增的行按 SQL 返回的顺序排列。
- `updateRows` 的 SQL 不用绑定变量。`entity` 为明细实体时 `recordKeyColumn` 是所属主单的主键，`rowKeyColumns` 写一列明细主键；为主表实体时不写 `rowKeyColumns`。主键列为空的行跳过；同一条记录的同一字段被写成不同的值时，返回 422 VALIDATION_FAILED。
- 两个动作用到的单据都加锁、做冻结检查，有一张被审批冻结时整个命令返回 409 FROZEN_BY_APPROVAL；改到的单据按各自的计算规则重算（write-pipeline 的 WP-18）。
- 例子：成本核算的"由BOM生成明细"要选中单据，是两个 `replaceDetails`，分别替换原辅料、包材：SQL 按旧 P_COST_BOM_INSERT 查 BOM 树 `CMX.T_COST_BOM_GOODS_TREE_V`，选出 `GOODSID`、`PER_HL`、`PRICE`，`binds` 为 `{"docId": "COST_PINGGU.DOCID", "goodsId": "COST_PINGGU.GOODSID"}`，物料按物料清单的分类归到原辅料或包材（与两个明细的读取视图相同）。"同步采购价"不用选中行（按钮的 `requiresSelection` 为 false），是两个 `updateRows`：原辅料的 SQL 为 `SELECT D.DOCID AS DOC_ID, D.DTLID AS DTL_ID, G.PRICE AS PRICE FROM V_COST_PINGGU_MATERIAL D JOIN T_COST_GOODS G ON G.GOODSID = D.GOODSID WHERE G.USEFLAG NOT IN ('产成品', '半成品') AND DECODE(D.PRICE, G.PRICE, 0, 1) = 1`，`recordKeyColumn` 为 `DOC_ID`，`rowKeyColumns` 为 `["DTL_ID"]`，包材换成 `V_COST_PINGGU_PACKAGE`；只选单价和参考价不同的行，只有这些单据加锁、重算。完整配置见 `backend/seed/config/operation.COST_PINGGU.generateFromBom.json`、`operation.COST_PINGGU.syncPrice.json`。

### 6.1 查找方式

`updateRecords` 用以下两种方式找目标：

- 按关联键：`{"kind": "relationKey", "entity": "COST_GOODS_PRICE", "targetKey": "GOODSID", "sourceKey": "COST_MATERIAL.GOODSID", "rows": "all"}`。按钮命令不带修改（C02 第 1 节），`rows` 只能为 `all`，用选中单据的全部行；来源行怎样取值，见 C08 第 9 节。
- 按关联 SQL：`{"kind": "sql", "entity": "COST_MATERIAL", "sql": "SELECT D.DOCID AS DOC_ID, D.DTLID AS DTL_ID FROM T_COST_PINGGU_DTL D WHERE D.GOODSID = :goodsId ORDER BY D.DOCID, D.DTLID", "binds": {"goodsId": "COST_GOODS_PRICE.GOODSID"}, "recordKeyColumn": "DOC_ID", "rowKeyColumns": ["DTL_ID"], "labelColumn": null, "displayColumns": []}`。绑定变量取来源单据的字段：只引用主表字段时执行一次；引用某个明细的字段时，按选中单据这个明细的每一行执行一次，主表字段取主表的值，各次的结果合并，同一对象只出现一次。绑定变量最多引用一个明细实体（第 10 节）。关联 SQL 不写 `rows`。
- `entity` 是找到的对象所在的实体。`recordKeyColumn` 取单据的主键：`entity` 为主表实体时就是这张表的主键，为明细实体时是它所属主单的主键，明细自己的主键放在 `rowKeyColumns`（C08 第 9 节）。
- 关联 SQL 只能是一条查询语句，参数用绑定变量，结果必须包含 `recordKeyColumn` 和 `rowKeyColumns` 中的每一列（第 10 节）；只读，不加数据库锁。查出的某一行主键列为空时，表示记录已不存在，跳过，不更新也不报错。

## 7. approvalFlow

审批流配在所属页面下（frontend-config FC-05），和旧系统一样分流程列表和三个 Tab：

- 流程：名称、所属页面、审核操作、启用、顺序（7.1）。
- 审批节点：每一级有哪些节点，每个节点的入口条件、发起部门限制、审批人和同级方式（7.3）。第 1 级的入口条件就是送审条件。
- 冻结节点：审批期间还要冻结哪些数据（7.4）。
- 展示数据：审批人看到哪些数据、勾选哪些行，全部级别通过后对勾选的行做什么（7.5）。

入口条件、关联条件和取值都写 SQL 片段，参数取这一行保存前、保存后的值（7.2）。

### 7.1 字段

| 字段 | 说明 |
|---|---|
| `page` | 所属页面，页面编码。这个页面的保存触发本审批流 |
| `order` | 顺序，整数。一张单据同时命中几个审批流时，全部通过后各审批流的操作按它从小到大执行，相同时按审批流编码（approval AP-10） |
| `enabled` | 是否启用。停用的审批流不触发 |
| `operations` | 审核操作：键为本页面的表格（主表实体或明细实体），值为 `add`（新增）、`modify`（修改）、`delete`（删除）的数组。至少一个表格选了一项操作。只有这些表格里做了这些操作的行，才交给第 1 级的入口条件判断 |
| `levels` | 审批节点，`[{"level": 1, "nodes": [...]}]`，级别从 1 开始连续，每级至少一个节点，见 7.3 |
| `freeze` | 冻结节点，见 7.4 |
| `display` | 展示数据，见 7.5 |
| `params` | `[{"name": "effectiveDate", "label": "生效日期", "type": "date", "source": "manual", "required": true, "level": 1}]`。每项必须写 `required`（是否必须有值）。`type` 取 `string`、`number`、`boolean`、`date`；`source` 取 `manual`（审批人在通过时填写，`level` 指在哪一级填写，最终批准时填写的不写 `level`）、`constant`（`value` 为常量）、`expression`（`value` 为 SQL 表达式，写法见 7.2）。取值中用 `:params_名称` 引用；中途某一级填写的参数也只在最终批准时使用 |
| `propagation` | 固定为 `end`，可以省略：通过后写入的数据不再触发审批 |
| `notify` | `[{"event": "submitted", "to": "levelApprovers"}]`。`event` 取 `submitted`、`levelEntered`、`passed`、`rejected`、`withdrawn`；`to` 取 `levelApprovers`、`applicant`、`{"users": […]}` 或 `{"role": "…"}`。通知文字由平台按固定格式生成，不在这里配置（approval AP-17） |

提交审批时，审批流定义随审批实例一起保存。之后再修改审批流配置，已经发起的审批不受影响，仍按提交时的定义走完；批准时的计算和校验按当时的规则执行。

### 7.2 参数和写法

入口条件、冻结和展示数据的关联条件、通过后操作的取值，都只写条件或表达式本身。approval 把它们包成完整的查询，在命令事务中只读执行，参数用绑定变量：

| 写的是 | approval 执行的语句 |
|---|---|
| 入口条件 | `SELECT 1 FROM DUAL WHERE (<条件>)`，查到一行即成立 |
| 冻结的关联条件 | `SELECT <冻结表的主键> FROM <冻结表> WHERE (<条件>)` |
| 展示数据的关联条件 | `SELECT * FROM <展示表或视图> WHERE (<条件>)` |
| 取值 | `SELECT (<表达式>) FROM DUAL`，取第一行第一列 |

| 参数 | 含义 |
|---|---|
| `:new_字段` | 本行修改后的值：合并本次修改并按计算规则重算后的值。删除行全为空 |
| `:old_字段` | 本行修改前的值：保存时加锁读到的数据库当前值。新增行全为空。本次没有修改的字段，与 `:new_` 相同 |
| `:master_new_字段`、`:master_old_字段` | 本行所属主表修改后、修改前的值；本行是主表行时与 `:new_`、`:old_` 相同 |
| `:operation` | 本行的操作：`added`、`modified`、`deleted` |
| `:billId` | 本行所属单据的主键 |
| `:user_id`、`:user_departmentId` | 发起人员的编号和所在部门的编号 |
| `:row_列名` | 只用于取值：修改表这一行的当前值 |
| `:params_名称` | 只用于取值：审批流参数的值（7.1 的 `params`） |

- 字段是实体的字段名（第 2 节 `fields[].name`）。
- "本行"：入口条件中是正在判断的那一行；冻结和展示数据的关联条件、取值中，是找到这条记录的那个触发本审批的行（7.3），每个触发行各执行一次。
- SQL 里查到的数据库数据都是保存前的值，本次保存还没有写入（approval AP-01）。
- 比较可能为空的值用 `DECODE`，例如 `DECODE(:new_PRICE, :old_PRICE, 0, 1) = 1` 表示单价改了，空改成有值、有值改成空也算。
- 片段里不能有分号。config 保存时把包好的语句交给数据库解析，语法错误或表、列不存在时拒绝保存（第 10 节）。

### 7.3 审批节点

| 字段 | 说明 |
|---|---|
| `name` | 节点名称 |
| `conditionType` | `always`：始终满足；`sql`：SQL 条件 |
| `condition` | `conditionType` 为 `sql` 时必须写，写法见 7.2 |
| `department` | 发起部门限制：部门编号，为 null 表示不限。发起人员不属于这个部门时，这个节点不满足 |
| `approvers` | 审批人：`{"type": "user", "userId"}`、`{"type": "role", "role"}`，或 `{"type": "sql", "sql": "SELECT USER_ID FROM …", "binds": {…}}`（进入该级时执行，只能是查询语句，返回用户编号） |
| `mode` | `or` 或签：任一审批人通过即可；`and` 会签：每个审批人都要通过，按角色配置时这个角色里任一账号处理，就算这个角色处理了 |
| `enabled` | 停用的节点不参与判断 |

- 保存时，`operations` 选中的表格里，做了选中操作的每一行（主表行也算一行），逐行代入第 1 级每个启用节点的入口条件；有一行成立，就进入这个节点。在任一第 1 级节点成立的行，是"触发本审批的行"；冻结、展示数据、通过后的操作都只用这些行。
- 第 1 级一个节点都没进入，这张单据按普通保存写入。进入了，这张单据整张冻结，本次对它的全部修改，包括没有触发审批的行，都随审批等待，通过后一起生效（approval AP-01）。
- 第 2 级起，只用触发本审批的行判断入口条件，有一行成立就进入这个节点。本级全部节点通过，才判断下一级；下一级一个节点都没进入，审批到本级结束（approval AP-04）。
- 任何人驳回，整个审批结束，修改都不生效。
- 一张单据同时命中几个审批流时，合成一个审批，同一级的节点合在一起审批；同一个人在本级多个节点里待处理，通过一次就都算通过（approval AP-01、AP-09、AP-16）。

### 7.4 冻结节点

`freeze` 每项：

| 字段 | 说明 |
|---|---|
| `table` | 冻结表：表名，可以不在平台注册。只能是表，不能是视图 |
| `condition` | 关联条件，写法见 7.2，每个触发本审批的行执行一次 |
| `enabled` | 停用的项不冻结 |

- 触发审批的单据总是整张冻结，不用配置。
- 冻结表在平台注册过（是某个实体的 `table`）时，查到的行所属的整张单据冻结：主从页为一行主表及其全部明细，单表页为这一行。没注册的表，只冻结查到的那一行。
- 冻结记录在提交审批的命令事务中登记，审批结束（通过、驳回或撤回）时解除。被冻结的数据不能修改、新增明细或删除，有人修改时返回 409 FROZEN_BY_APPROVAL，前端弹出冻结它的审批的进度（frontend-page FP-16）；只有来源为本审批的写入可以修改（approval AP-03）。
- 同一份数据同一时间只属于一个未结束的审批。要冻结的数据已被别的审批冻结时，整个命令返回 409 FROZEN_BY_APPROVAL（approval AP-06）。
- 冻结什么完全由配置决定。展示数据中要修改、却没有冻结的行，审批期间别人可以修改；最终批准写它之前，write-pipeline 给它加数据库行锁并做冻结检查（WP-18）。

### 7.5 展示数据

`display` 是块的数组，按顺序显示，也按顺序执行。每块：

| 字段 | 说明 |
|---|---|
| `key` | 块的编码，本审批流内唯一；审批人提交勾选时用它指出是哪一块 |
| `title` | 展示标题 |
| `region` | `master`：修改内容 · 主表；`detail`：修改内容 · 明细；`affected`：受影响单据 |
| `source` | `master`、`detail`：本页面的表格（主表实体或明细实体）。`affected`：表名或视图名，可以不在平台注册 |
| `condition` | 关联条件，写法见 7.2。`affected` 必须写：每个触发本审批的行执行一次，结果按修改表的主键合并，同一行只出现一次，并记下找到它的触发行。`master`、`detail` 可以不写：不写时 `master` 显示这张单据，`detail` 显示这张表本次新增、修改、删除的行；写了时对这张表的每一行判断，参数取这一行，显示成立的行 |
| `targetTable` | 只用于 `affected`：修改的表。`source` 是表时省略，就是这张表；`source` 是视图时必须写 |
| `keyColumn` | 只用于 `affected`：`source` 中修改表主键所在的列，只能是一列。`source` 是表时省略，取这张表的主键；是视图时必须写。由配置的人保证正确，配错时执行报错 |
| `columns` | 显示列，每项 `{"field": "PRICE", "label": "单价", "precision": 2, "width": 120, "targetColumn": "PRICE"}`。`field` 为 `source` 的字段或列；修改表在平台注册过时，还可以写 `master.字段`，取这一行所属单据主表的字段。`precision`、`width` 可以省略。`targetColumn` 只用于 `affected`，指出这一列对应修改表的哪一列，省略时按同名对应 |
| `selection` | 只用于 `affected`：`checked` 默认全选、审批人可以取消；`all` 全部执行、不能取消；`hidden` 不给审批人看、通过后全部执行 |
| `actions` | 只用于 `affected`：全部级别通过后，对勾选的行按顺序执行的操作，见下表。`master`、`detail` 的操作固定为应用本次修改，不写 |

| `action` | 参数 | 作用 |
|---|---|---|
| `updateFields` | `fields`：`[{"column": "ZX_PRICE", "value": ":new_PRICE"}]` | 按主键修改修改表的这一行：`column` 为修改表的列，`value` 为取值（7.2） |
| `insertRows` | `table`、`fields` | 每个勾选的行在 `table` 中新增一行，`fields` 同上；主键取序列 `<表名>_SEQ`（第 2 节） |
| `deleteRows` | 无 | 按主键删除修改表的这一行；修改表注册过且是主表时，连同明细删除整张单据 |
| `escapeHatch` | `operation`：已登记的逃生舱操作 | 调用存储过程，只在用户点名时启用 |

- 勾选框按修改表的主键分：主键相同的几行合成一个勾选框，`master.` 的列合并显示。例如 `source` 每行是一条明细、修改表却是主表时，同一张单据的几行只有一个勾选框。
- 修改表在平台注册过时，写入按所属页面的保存处理：校验、按计算规则重算、记审计（write-pipeline）。这一行属于哪个实体，按"表 + 主键"找出；同一张表属于几个实体时（例如原辅料和包材都写 T_COST_PINGGU_DTL），取读取视图里查得到这一行的那个实体。没注册的表，按主键直接改写入的列，不重算。
- 同一条记录要被写成不同的值时，保存那一刻就拒绝，返回 422 VALIDATION_FAILED，提示是哪条记录、哪两个值。例如一张成本单里两行聚维酮K30，一行改成 80、另一行改成 82，都要写物料清单里聚维酮K30 的执行价。
- 查出的某一行 `keyColumn` 为空，表示记录已不存在：在这一块最后显示为红底的"记录已不存在"，不能勾选，执行时跳过（approval AP-21）。
- 修改表、`insertRows` 的 `table` 不能是平台自己的表（`PF_` 开头）。

### 7.6 审批详情

- 样式同旧系统：审批进度；`master` 块一张表；`detail` 块每块一个 Tab，带"变化"和"触发审批"两列；`affected` 块每块一个 Tab，标题后显示条数（frontend-approval FA-06）。
- 修改前是数据库中的当前值：冻结的数据审批期间不会变，就是保存时的值；没冻结的，取打开详情那一刻的值。
- 修改后：`master`、`detail` 为当前值加上全部待审修改，再按计算规则重算；`affected` 为当前值加上勾选的行要写的值，修改表注册过时，再按所属页面的计算规则重算这一行所属的单据（包括 `master.` 列）。`affected` 中按 `targetColumn` 对应得上修改表的列，才显示修改后；视图自己算出来的列只显示当前值。修改前、修改后不同时显示"75 → 80"，相同时只显示当前值。
- 新增的行标为"新增"，只显示新值；删除的行标为"删除"，显示删除前的值。小数位取 `precision`，没写时取页面视图。
- 审批人勾选或取消勾选后，详情按当前勾选重新计算修改后（C09 第 6 节的预览）；通过时提交当前勾选，后台再算一遍，和审批人看到的不一致时返回 409 RECONFIRM_REQUIRED（approval AP-08）。
- 多级审批时，下一级只能看到上一级保留的行，只能再取消，不能把上一级取消的行勾回来（approval AP-07）。
- 几个审批流合成的审批：来源单据只显示一份，列取各审批流 `master`、`detail` 块的并集，按 `order` 排列；明细每行"触发审批"列出这一行触发的审批流，没有触发的显示"随审批等待"。各审批流的 `affected` 块各自一个 Tab，标题后注明审批流名称。
- 没有配置 `master`、`detail` 块时，来源单据的主表显示有变化的字段，每个明细表一个 Tab，显示有变化的行和字段。
- 以上修改前、修改后的取法用于待审的审批。已结束的审批（通过、驳回、撤回）显示结束那一刻的修改前、修改后：结束时按上面的取法算一次存下，以后数据怎么变都不影响（approval AP-23）。例如成本单 2550 的聚维酮K30 单价 90 改成 75 的审批通过后，打开它仍显示"90.00 → 75.00"。结束时没有存下、也不能从已有记录还原的，详情写明结束时的值没有保存，不显示修改内容。来源：用户 2026-10-30 要求"已结束的审批显示结束时的值"；对照旧系统，已结束的审批显示送审时存下的展示快照，查看时不再执行展示 SQL（`ApprovalPresentationService.readSnapshot`），没有快照时显示"该审批未保存修改内容展示数据"（`ApprovalDetailDialog.vue`）。

### 7.7 全部级别通过后

1. 先应用来源单据的修改，整张单据一起生效。
2. 再按 `order`，各审批流按 `display` 的顺序，对每个 `affected` 块勾选的行（`all`、`hidden` 为全部行，记录已不存在的不算）执行 `actions`。取消勾选的行不改。
3. 以上在同一个命令中执行，执行上下文的来源为本审批；`propagation` 为 `end`，这些写入不再触发审批。任何一步出错，整次通过回滚，审批停在本级，返回错误。

### 7.8 样例一：成本明细改价审批

成本核算的原辅料、包材新增或修改后，物料或单价有变化、并且单价和物料清单的单价（执行价为空时取参考价格）不一样，进入审批。系统管理员审批；第 2 级为示例：单价比清单价高 10% 以上时，再由采购、生产会签。冻结物料清单里的这个物料；通过后把单价写到物料清单的执行价。

- 第 1 级逐行判断：聚维酮K30 单价改了，90 和清单价 75 不同，成立；微晶纤维素物料改了，但 40 和清单价 40 相同，不成立；硬脂酸镁物料、单价都没改，不成立。只有聚维酮K30 这一行触发本审批，2550 整张冻结，三行修改都随审批等待。
- 冻结和受影响单据都只用聚维酮K30 这一行：物料清单里只冻结、只显示聚维酮K30，单价 75 → 90，不能取消。物料清单一块展示视图 `T_COST_GOODS_PRICE_V`，执行价为空时显示参考价格，所以修改前是 75；写入的是表 `T_COST_GOODS` 的 ZX_PRICE。
- 第 2 级：90 大于 82.5，进入"采购、生产会签"，采购和生产都通过才算本级通过。单价只改到 80 时，第 2 级不成立，管理员通过就结束。
- 全部通过后，三行修改一起生效，物料清单里聚维酮K30 的执行价变成 90。

## 8. role

```json
{
  "name": "成本会计",
  "admin": false,
  "pages": {
    "COST_PINGGU": {
      "buttons": ["system:save", "system:advancedSearch", "master:modify", "master:copyRow", "master:syncPrice", "COST_MATERIAL:addRow", "COST_MATERIAL:deleteRow", "COST_MATERIAL:modify", "COST_MATERIAL:copyRow", "export:cost-pinggu-export"],
      "rows": {"mode": "visual", "logic": "AND", "conditions": [{"field": "CREATE_BY", "fieldLabel": "创建人", "op": "eq", "valueType": "dynamic", "value": "${username}"}], "sql": "CREATE_BY = ${username}"},
      "columns": {"master": {"PRICE": {"visible": true, "editable": false}}, "COST_MATERIAL": {}}
    }
  }
}
```

- `rows` 是行权限，格式与旧系统相同，有两种写法：
  - 可视化：`mode` 为 `visual`；`logic` 为 `AND` 或 `OR`；`conditions` 每项含 `field`、`fieldLabel`、`op`、`valueType`（`static` 或 `dynamic`）、`value`；`sql` 是按条件生成的 SQL 条件。`op` 取 `eq`、`ne`、`gt`、`ge`、`lt`、`le`、`like`、`in`、`isNull`、`isNotNull`。
  - 自定义 SQL：`rows` 直接是一个 SQL 条件字符串，例如 `"CREATE_BY = ${username}"`。
- 两种写法都可以用占位符 `${userId}`、`${username}`。平台把占位符换成绑定变量执行，不拼接字符串。
- 保存时校验：SQL 条件只能是一个条件表达式，不能含分号和数据修改语句。
- 没有 `rows` 时，可以访问页面主表的全部行；明细随主表。
- `buttons` 是按钮权限，与旧系统的 BUTTON_POLICY 相同，区别是分组改用区域编码、新增删除修改按区域给（v24），界面上仍显示区域标题。区域是 `master`（主表）或明细实体编码（例如 `COST_MATERIAL`），单表页只有 `master`：
  - `system:<动作>`：页面级按钮，取 `save`（保存，没有时整页只读）、`advancedSearch`（高级查询）；
  - `<区域>:addRow`、`<区域>:deleteRow`、`<区域>:modify`：这个区域的新增、删除、修改，例如 `master:modify`、`COST_MATERIAL:addRow`；
  - `<区域>:<其他动作>`：区域中的其他按钮，例如 `master:copyRow`、`master:syncPrice`、`COST_MATERIAL:saveGridConfig`；
  - `export:<导出编码>`：可以使用的导出配置；
  - `["*"]` 表示该页面的全部按钮、导出，以及每个区域的新增、删除、修改。
  - `system:addRow`、`system:deleteRow`（v24 之前的页面级新增、删除）不再起作用。
- 新增、删除、修改的含义：
  - 修改：没有某个区域的 `modify` 时，这个区域已经保存的行全部字段都不能改，列权限（`columns`）和界面规则只能在这个基础上再收紧；新增的行、复制出的行照常填写，不需要修改权限。
  - 新增：没有 `addRow` 时，这个区域不显示"新增"按钮。复制出的行在后端也是新增行，要这个区域的 `copyRow` 或 `addRow`。
  - 删除：没有 `deleteRow` 时，这个区域不显示"删除"按钮。删除主表行连同它的明细（write-pipeline 的 WP-06），只看 `master:deleteRow`。
- 后端按 `buttons` 检查（authz 的 AZ-01）：保存需要 `system:save`；Patch 中的新增行需要所在区域的 `addRow` 或 `copyRow`；已有行的修改需要所在区域的 `modify`；删除需要所在区域的 `deleteRow`；按钮操作需要该按钮的键；按导出配置导出需要 `export:<编码>`；默认导出当前页面不需要单独授权。按钮动作写的行（例如"由BOM生成明细"在原辅料新增的行）只看按钮自己的权限，不看新增、删除、修改。审批的处理由审批流决定，不使用按钮权限；审批通过时的写入只拒绝计算字段和 ERP 列（7.5）；审批进度所有人都能查看。
- 例：角色在成本核算只有 `system:save`、`COST_MATERIAL:addRow`、`COST_MATERIAL:deleteRow`、`COST_MATERIAL:modify`：主表的单据不能改，没有主表的新增、复制、删除；原料/辅料能改已有的行、能新增和删除行；包材没有新增、删除按钮，已有的行不能改（业务例子 E42）。
- `columns` 是列权限，格式同旧系统的 COLUMN_POLICY，按区域列出字段的 `visible`、`editable`、`required`，只能收紧可见、可编辑，或增加必填。
- `admin` 必须写，为 true 的角色可以使用配置和管理功能。

## 10. 保存时的校验

config 保存任何配置项时都执行以下校验，不通过时拒绝保存（422 VALIDATION_FAILED），当前版本不变：

- 引用的实体、字段、操作、页面、审批流、Lookup、字典都存在。
- 表和列在数据库中存在（经 db-core 的 `SchemaInspector`）。
- 没有 `erpRow` 的实体，其 ERP 列在任何层都不能设为可写，也不能出现在 `writableFields` 和 `fieldMapping.to` 中；任何实体的 ERP 列都不能出现在逃生舱的 `writes` 中；`erpRow.column` 不能设为可写。
- 下层只能收紧可见、可编辑，必填只能增加。
- `formLayout` 不越出 24 列，不引用不存在的字段。
- 页面字段的 `aggregate` 只能用于数值字段（实体字段的 `type` 为 `number`）。
- 表达式和条件能被 rules-core 解析，计算规则的依赖不成环，规则包能编译通过。
- 关联 SQL、数据项 SQL 和导出 SQL 只能是一条查询语句，参数用绑定变量；关联 SQL 的结果包含 `recordKeyColumn` 和 `rowKeyColumns` 中的每一列，导出 SQL 的结果包含 `keyColumn` 或 `linkColumn`。例如 `rowKeyColumns` 填了 `DTL_ID` 而 SQL 没有选出这一列时，拒绝保存，提示缺少的列。
- 审批流的 SQL 片段（入口条件、关联条件、取值，7.2）不含分号，按 7.2 包好后交给数据库解析，语法错误或表、列不存在时拒绝保存；参数只能是 7.2 列出的几种：`:new_`、`:old_` 后面的字段属于 `operations` 中的某个表格（`master`、`detail` 块的关联条件中，属于这一块的表格），`:master_` 后面的字段属于所属页面的主表实体，`:row_` 后面是修改表的列，`:params_` 后面是本审批流的参数。
- 审批流的 `page` 是已有页面；`operations` 的键是这个页面的主表实体或明细实体，`freezable` 为 true，操作只能取 `add`、`modify`、`delete`，至少一个表格选了一项。
- 审批流的级别从 1 开始连续，每级至少一个节点，每个节点至少一个审批人；`conditionType` 为 `sql` 时必须写 `condition`；`department` 是已有部门。
- 审批流 `freeze[].table` 在数据库中必须是表，不能是视图（经 `SchemaInspector` 的 `object_type`），不能是 `PF_` 开头的平台表；注册过的表，所属实体的 `freezable` 必须为 true。
- 审批流的 `display`：`key` 在本审批流内不重复；`master` 块的 `source` 是所属页面的主表实体，`detail` 块是它的明细实体，这两种块不写 `targetTable`、`keyColumn`、`selection`、`actions`。`affected` 块必须写 `condition`、`selection`；`source` 在数据库中是表或视图，是视图时必须写 `targetTable` 和 `keyColumn`；`targetTable`、`insertRows` 的 `table` 是表，不能是 `PF_` 开头的平台表；`columns[].field` 是 `source` 的列，`master.` 开头的只能在修改表注册过时使用，字段属于它所属的主表实体；`updateFields` 的 `column` 是修改表的列，修改表注册过时不能是计算字段或 ERP 列。
- 页面区域按钮的 `action` 为业务动作时，必须写 `operation` 和 `requiresSelection`；为内置动作时，这两项都不能写。
- `kind` 为 `action` 的操作中，`updateRecords` 按关联键查找时 `rows` 只能为 `all`：按钮命令不带修改（C02 第 1 节），没有"本次有变化的行"。
- `replaceDetails` 的 `entity` 是明细实体，`binds` 只引用它所属主表的字段；`updateRows` 的 SQL 不用绑定变量，结果包含 `recordKeyColumn` 和 `rowKeyColumns` 中的每一列，`entity` 为明细实体时 `rowKeyColumns` 写一列，为主表实体时不写。两者的 SQL 只能是一条查询语句，交给数据库解析；结果中其余每一列都是 `entity` 的字段，在本操作的 `writableFields` 中，不是计算字段、只在视图中的字段或只读的 ERP 列。例如"由BOM生成明细"的 SQL 多选了 `BATCH_QTY`（每批数量，计算字段）时，拒绝保存，提示这一列由计算规则得出。
- `approvalRequired` 的每条规则，至少有一个启用的审批流的 `page` 在 `sourcePages` 中。
- 实体的 `updatedByColumn` 是 `table` 中的列，不是任何实体字段的 `column`。
- 实体的序列 `<表名>_SEQ` 必须已在数据库中存在；平台不创建序列。
- 审批人 SQL、`compare.source` 只能是查询语句或表、视图名，参数用绑定变量；`manual` 参数的 `level` 必须是该审批流已有的级别。
- 仍被其他配置引用的配置项不能删除。
