# contracts

状态：已确认。上级：[架构与组装](../架构与组装.md)。

## 1. 职责

- 负责：维护契约 C01–C11 的定义；在后端和前端代码中实现契约的类型和端口协议；为每个后端端口、管道阶段和 HTTP 接口提供替代实现；提供契约测试。
- 不负责：任何业务逻辑和真实实现，它们由各提供方模块负责（见[架构第 8 节](../架构与组装.md)）。

## 2. 所有权

| 类别 | 内容 |
|---|---|
| 文档 | `docs/契约/` |
| 代码 | `backend/src/cost_platform/contracts/`（`types.py`、`ports.py`、`fakes/`）、`frontend/src/contracts/` |
| 测试 | `backend/tests/contracts/`、`frontend/tests/contracts/` |
| 数据、配置、状态 | 无 |

## 3. 对外契约

- CT-01：按 C01 在 Python 和 TypeScript 中各实现十进制文本的解析、格式化和数值一致的判定，用 C01 的全部样例测试。Rust 的实现归 rules-core。
- CT-02：按 C02–C11 实现类型，其中 C06 只定义配置的数据结构，第 10 节的保存校验归 config（CF-01）。后端进出 JSON 的类型用 pydantic 模型，经统一的解析和输出函数按 C01 第 1 节处理；模块之间传递的类型用 dataclass；端口用 Protocol。前端用 TypeScript 类型。
- CT-03：C08 的每个端口和管道阶段都有内存替代实现，测试可以预设它的返回值和错误。
- CT-04：C09 的每个接口都有前端模拟实现，返回 C09 中的样例。
- CT-05：每个端口一套契约测试。替代实现和各模块的真实实现运行同一套测试。
- CT-06：修改契约时，按[架构第 5 节](../架构与组装.md)执行：写明改动、受影响的模块和任务，用户确认后版本号加一，同步更新类型、替代实现和契约测试。

## 4. 依赖

无。

## 5. 内部流程

1. 按 C08 重写 `backend/src/cost_platform/contracts/` 中已有的草稿；`adapters/system.py` 中的系统时钟和编号生成移到 assembly，`adapters/` 目录删除。
2. 先写类型和端口，再写替代实现，最后写契约测试。
3. 前端类型与后端类型字段一一对应，用 C02、C05、C09 的样例互相核对。

## 6. 接入方式

全部模块都依赖本模块。本模块属于第 0 组，完成后其他模块才能开始开发。

## 7. 验收边界

- 开始开发的前置条件：架构已确认，C01–C11 已确认。
- 本模块完成：类型、端口、替代实现和契约测试都能运行；替代实现通过全部契约测试；前后端类型能无损解析契约中的全部样例。
- 联调后才能确认：真实实现是否通过同一套契约测试，由各提供方模块和 assembly 确认。
