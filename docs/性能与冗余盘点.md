口径：

## 4. 写入链路

| 编号 | 位置 | 现象 | 改法 | 依据 |
|---|---|---|---|---|
| W-01 | `db_core/engine.py` 的 `pool_pre_ping=True` | 每次取连接多一条 `SELECT 1 FROM DUAL`，所以改一格是 5 条（目标 4）、提交相同值是 3 条（目标 2） | 去掉 `pool_pre_ping`，改用 `pool_recycle` 加上现有的断线错误映射，或者改用 oracledb 自带连接池（Thin 模式的探活不是 SQL）。顺带设置 `pool_size` 和 `stmtcachesize` | 核实 |
| W-02 | `approval/trigger.py` 的 `_entered`、`_freezes`、`_affected`、`_conflicts`；`approval/store.py` 的 `freeze` | 入口条件、冻结、受影响单据都按每个触发行执行一次 SQL；冲突检查对每个受影响行单独查目标行，再逐个取值；冻结记录逐条插入 | 一条命令内按"SQL 文本加绑定值"缓存结果（`binds_for` 只绑定语句里用到的变量，只引用主表字段的条件自然只执行一次）；目标行按块一次查完；冻结记录、勾选状态、通知登记改为批量插入 | 核实 |
| W-03 | `approval/process.py` 的 `ResolveStage`、`ProcessStage._pass`、`_finish`；`queries/documents.py` | 审批记录读两次（第二次加锁）；`Evaluator.compute` 在 `_pass` 和 `_finish` 各算一次；DocumentReader 在命令事务外另开连接读单据，不加锁，之后同一批单据又被加锁读一遍 | 只加锁读一次审批记录；复用第一次的计算结果；用已加锁读到的单据 | 重复是核实，减少的比例是推测 |
| W-04 | `operations/actions.py` 的 `find_targets` | `updateRecords` 按来源明细逐行调用 `RelatedQuery.find`，N 行就是 N 条 SQL | 按关联键一次查完再分回各来源行；关联 SQL 先按绑定值去重 | 核实 |
| W-05 | `delivery/service.py`、`delivery/worker.py`、`delivery/tables.py` | 提交后每个接收人 5 条 SQL；PF_DELIVERY 只有主键索引、发送过的记录不清理，每 60 秒一轮的重试全表扫描 | 加 `(status, next_retry_at)` 索引（走 delivery 的迁移脚本）；批量领取、批量写入。是否去掉投递记录这一层见待确认 3 | 核实 |
| W-06 | IN 列表 | 键数每变一次就是一条新的 SQL 文本，Oracle 多一次硬解析 | 键数补齐到固定档位（例如 10、100、1000） | 代码核实，性能影响推测 |
| W-07 | 冻结检查 | 每张可冻结的表 1 条，与加锁读取分开执行 | 并进加锁读取的那条 SQL | 推测，要在 Oracle 上验证 |

已经做得好的部分：每个实体一条 `FOR UPDATE` 读主表，多个明细实体一条 `UNION ALL`，写入用 `executemany` 和 `RETURNING`，审计差异和命令结果合在同一条 UPDATE 里，每张单据只调用一次规则求值。

## 5. 读取链路与实时

| D-02 | `queries/sql.py` 的 `Conditions.build` | 文本条件一律写成 `UPPER(列)`，非文本列的 LIKE 写成 `TO_CHAR(列)`，包含匹配是 `'%x%'`，用不上索引 | 精确匹配和开头匹配建 `UPPER(列)` 函数索引，排序列建（排序列、主键）复合索引；索引是 DDL，要人工执行 | 写法核实，性能影响推测 |
| D-03 | `queries/exports.py`、`queries/xlsx.py` | 导出把全部行放进内存，按配置导出时还复制一份，最后整体拼成字符串再压缩返回；10 万行×30 列峰值估计 0.6–1GB | 换 XlsxWriter 的 `constant_memory` 模式，写临时文件，用文件流返回（见待确认 1） | 做法核实，内存是推测 |

## 9. 待确认

1. 导出要不要加 XlsxWriter 依赖（D-03、K-01）。场景：导出全部成本单明细 10 万行，现在估计要占 0.6–1GB 内存，加了以后内存基本不随行数增长。
2. 判重要不要挪到命令末尾，和命令结果合成一条 SQL，每次保存再少 1 条。后果：同一个保存请求被连点两次时，第二次的提示从"请求正在处理"变成"单据正被其他人修改，请稍后再试"；两种情况数据都只保存一次。要改 WP-01。
3. 通知要不要去掉投递记录这一层（W-05）。改法：站内通知在保存的同一个事务里写入，提交后推送，PF_DELIVERY 表和每 60 秒的扫描都去掉。后果：用户看到的通知不变；以后加企业微信这类需要重试的渠道时，要把投递记录加回来。要改 DL-01 到 DL-05。
4. 可以评估、不急：配置的 Redis 副本方案（config 的 CF-04 到 CF-06）改成"代号变化时增量读 Oracle"，可以去掉 Redis 里的配置内容、待生效登记和删除标记。"保存即生效"不变，但这是已确认的设计，要单独评估。
