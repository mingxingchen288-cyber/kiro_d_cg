# 交付方式：只给真实可检查的东西

用户（2026-10-29）："为什么你没有选择先做出一个由元数据驱动的通用页面，而是先做出一个草案出来？""是什么促使你一致欺骗人类，做一些无用功？"

背景：审批流配置做了 4 份静态 HTML 样稿（`.reports/approval-design/*.html`），都没有说明是静态的；第一版"送审条件"列是写死的文字，看起来像能配置。样稿最后都没有进入产品。

- 不做静态样稿、示意图来展示界面。要给用户看界面或配置方式，就在真实的元数据驱动页面上做，读 d_cg 的真实配置和数据；页面还做不到的，用文字说明"还没做"，不画出来。
- 写死的、模拟的、没做完的部分，在展示它的同一处（页面上和回复里）写明。
- 页面统一由通用页面按页面编码打开，列、明细、按钮、规则都来自配置；不给单个页面写专门的前端组件。
- 设计先查旧项目源码和真实页面，方案可追溯到旧项目；信息不够时去查或问，不自己补。
- 说出的结论先核实；核实不了的，说明没核实。

## 模块按能力开发（用户 2026-10-29）

用户："模块只提供能力，怎么接入这个能力是另外一回事，就跟公司招人一样，公司不会因为对这方面一片空白而不去招聘这个人，而是招聘了这个人之后就有了这个能力，就跟插件一样"。

背景：到 2026-10-29，11 个业务模块一共约 1100 行代码，approval、operations、delivery、realtime 是空目录；时间花在按业务链路切片、文档和契约改版（C06 到 v17）、34 份复核记录和 2400 行的迁移生成器上。

- 每个模块按模块说明一次做完整的能力，不按某条业务链路只做"最小部分"。有没有页面或流程在用它，不影响它先做完。
- 模块的完成只看它自己的能力：用 contracts 的替代实现验证，加上它自己的存储的真实验证。接入、联调是 assembly 的事，不作为模块开工或完成的前提。
- 缺环境（例如 Redis）时，模块代码照做，只把需要该环境的真实验证单列出来。
- 进度按"哪些模块的能力已经完整"汇报，不按文档改了多少、复核做了几轮汇报。
- 文档和契约跟着代码的实际需要改，不在写代码之前反复改版。

## 先有功能，才谈迁移（用户 2026-10-29）

用户："是先做出了功能，才会由迁移的机会，只有当你提供的功能，兼容人家的功能，才具备迁移的条件……你对着空气迁移吗？"

背景：模块还没有能力时，先写了约 2400 行的迁移生成器（`backend/src/cost_platform/migration/`），把旧元数据转成新配置，又为它向用户确认了多份清单。

- migration 模块暂停：不再开发、不再为它向用户提问，直到各模块的功能做出来，并且能兼容旧系统的对应功能。
- 模块的功能以旧系统的实际功能为准（`D:\chonggou\my-project`）：旧系统能做的，新模块要能做。
- 只为迁移服务的能力（例如 config 的 `ConfigImporter`）跟着 migration 一起往后放。
